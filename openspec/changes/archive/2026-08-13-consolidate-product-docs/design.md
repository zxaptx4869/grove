## Context

初始化阶段将 `docs/项目上下文与文档路由.md` 设计为文档入口，同时 `PROPOSAL.md` 承载产品提案和技术选型。随着产品蓝图形成，两份旧文档与 `README.md` 出现职责重叠，且旧提案包含已经失效的产品范围。现有 `project-workflow` 主规格仍强制要求旧路由文件存在，因此删除前必须同步修改规格和仓库执行规则。

## Goals / Non-Goals

**Goals:**

- README 成为仓库唯一文档导航和快速上手入口。
- 产品蓝图成为产品范围、优先级及长期技术选型的权威基线。
- AGENTS 只保留代理守则、工作流和工程约定。
- OpenSpec 主规格与新的文档结构一致。
- 删除重复、过时且容易误导实现代理的两份旧文档。

**Non-Goals:**

- 不修改业务能力、运行时代码或数据。
- 不重写已归档 OpenSpec 工件中的历史描述。
- 不在本 change 调整产品蓝图的功能优先级。

## Decisions

### D1：README 作为唯一文档入口

README 同时提供项目简介、权威文档索引、目录结构、本地开发和质量检查命令。新协作者无需先打开另一个“路由文档”才能找到产品蓝图和 OpenSpec。

**备选：** 保留独立文档路由。未采用，因为它只重复 README 内容，且增加两处同步维护成本。

### D2：产品蓝图吸收仍有效的技术决策

在产品蓝图新增“技术与工程基线”，保留：前后端技术栈、数据库、PydanticAI 与 Provider 分层、云端 OCR 评测、任务管道、附件存储、搜索演进、认证、部署、移动端和 OpenSpec。删除已经被蓝图替代的旧 MVP、旧路线和大型装修模板判断。

**备选：** 新建独立技术选型文档。未采用，因为当前技术决策规模有限，产品蓝图与技术边界关联紧密；后续复杂架构仍应记录到具体 change 的 `design.md`，无需再增加全局入口。

### D3：历史工件不追溯改写

`openspec/changes/archive/` 和初始化任务书中的旧路径引用保留。它们描述当时的仓库状态，批量改写会损害历史可追溯性。当前入口、守则和主规格不再引用已删除文件。

### D4：主规格修改而非绕过

将 `文档路由可寻址` 的要求改为 `README 文档入口可寻址`，完整保留“新协作者能找到权威文档”的行为目标，只改变实现载体。

## Risks / Trade-offs

- [外部书签仍指向被删文档] → README 与产品蓝图路径稳定；仓库内当前引用全部更新，历史工件明确不作为入口。
- [蓝图过长] → README 提供分层入口；蓝图使用清晰章节，技术基线集中在单独一节。
- [产品与技术决策再次混杂] → 蓝图只承载长期基线，change 级技术细节仍进入对应 `design.md`。
- [删除文件造成主规格失败] → 先创建 delta spec，完成编辑后运行 `openspec validate --all --strict` 并在归档时同步主规格。
