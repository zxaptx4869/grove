## Why

确认台目前只能逐条按 Source 处理候选；当多条来源的候选都「推荐明确」时，用户仍要一一点开确认，效率低。P0-B 的批量处理需要让用户在确认台内一次处理多个 Source 的低风险候选，同时保证高风险项继续走逐条精审。

## What Changes

- 确认台增加「按采集审阅 / 批量处理」切换，两个视图共享同一批待采纳候选，不存在“整 Source 自动全采纳”的语义。
- 新增项目级批量候选列表：返回项目内全部待采纳候选，并标记 `review_band`（快审/精审）。
- 批量视图按推荐目录分组展示快审候选，并提供「批量确认并归档」「批量拒绝」「修改目录」动作；精审候选集中展示、勾选禁用，可一键回到逐条审阅。
- 批量确认逐条创建 Entry：成功项保留、失败项留在列表可重试（partial），默认使用候选推荐节点，也可用「修改目录」统一覆盖。

## Capabilities

### New Capabilities

- `batch-candidate-review`: 跨 Source 批量候选视图、按推荐目录分组、批量确认/拒绝/改目录、精审分流与逐条 partial 语义。

### Modified Capabilities

- `candidate-review`: 确认台提供「按采集审阅 / 批量处理」切换，并共享同一候选池与处理状态。

## Impact

- 后端：新增项目级待审候选列表接口与项目级批量决策接口；服务层新增快审/精审分流与逐条归档；`schemas/review.py` 扩展请求/响应模型；补充后端测试。
- 前端：`ReviewPage` 增加模式切换；新增批量视图组件与 API 客户端、查询键；补充前端测试。
- 无新外部依赖。

## Non-Goals

- 不做与已有 Entry 的关系建议（`add-entry-relation-suggestions`），本轮不使用“疑似重复/可能冲突”等关系标签。
- 不做类型、来源、风险筛选器。
- 不做跨项目批量处理。
- 不做整批原子回滚：批量确认按候选逐条成功/失败返回。
