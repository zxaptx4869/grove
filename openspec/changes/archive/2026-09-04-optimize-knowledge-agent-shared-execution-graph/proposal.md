## Why

第一阶段复合回答已经能把多个回答义务映射为多份 Grove 检索或结构化请求，但服务端仍按请求逐份串行执行；语义相同的集合、重复检索和同一集合上的多个输出可能被重复计算，既增加延迟与调用成本，也使同一回答中的结果更容易因独立执行而产生不一致。现在需要在不扩大 Agent 自主权的前提下，把已固化计划编译为应用控制的共享只读执行图，为后续只补真实缺口的有界覆盖修复提供稳定复用基础。

## What Changes

- 新增版本化共享执行图：把已规范化的复合回答请求编译为受限的数据集节点、Evidence 读取节点和输出节点，并保存义务与节点的关联。
- 由服务端基于规范化参数生成稳定节点指纹，合并等价集合与重复读取；模型不能指定指纹、授权范围、执行优先级或任意依赖。
- 校验图节点类型、依赖、无环性、消费者、数量、深度、字节与总执行预算；非法图不执行，并显式回退现有第一阶段串行执行器。
- 按确定性拓扑顺序调度节点；只对已验证互不依赖、只读且受同一 Run 预算控制的节点安全并行，其他节点保持串行。
- 在同一 Run 内复用已完成节点结果，按节点提交有界检查点；Worker 恢复只重放未完成节点，不重新规划或重复执行已提交节点。
- 保持现有 `answer`、`points`、Citation、逐项覆盖、实际依据和客户端投影不变；最终综合继续只接收服务端验证后的 Evidence、工具事实与缺口。
- 扩展节点级工具审计、耗时、状态、完整性、复用与 fallback 记录，禁止并行或复用掩盖真实失败。
- 使用独立特性开关渐进启用；开关关闭或图编译/校验失败时继续使用已上线的固定一次执行路径。

**Non-Goals:**

- 不根据覆盖结果生成第二份计划、第二轮补查或自主工具循环；这些属于 `add-knowledge-agent-bounded-coverage-repair`。
- 不迁移既有 investigate 执行图，也不统一 quick、investigate 与 entries 的全部运行时。
- 不改变第一阶段复合计划的用户可见回答义务、回答协议或原生端交互。
- 不接入外部搜索、知识写入、`prepare_operation`、多 Agent 协商或后台无限任务。
- 不跨 Run、跨 Conversation 或跨 Workspace 共享查询结果，不建设通用分布式缓存。

## Capabilities

### New Capabilities

- `knowledge-agent-shared-execution-graph`: 定义复合回答计划到受限共享只读执行图的编译、等价节点合并、依赖校验、确定性调度、安全并行、节点检查点与恢复复用。

### Modified Capabilities

- `knowledge-agent-composite-answer-planning`: 将已固化复合计划的执行从“按请求固定串行”扩展为可由特性开关启用的服务端共享执行图，同时保持最终综合与覆盖协议不变。
- `knowledge-agent-run`: 增加共享图的版本化快照、节点级恢复、取消、预算和可观测约束，旧 Run 与旧执行快照继续可读。

## Impact

- 后端 Knowledge Agent 复合回答计划规范化、执行器、结构化查询 dispatcher、Evidence 读取、Worker 恢复与可观测服务将受到影响。
- `knowledge_agent_runs` 需要追加可空、版本化且有字节上限的共享图/节点执行快照字段；迁移必须兼容 SQLite 与 MySQL 8，不回填旧 Run。
- 可能新增并行度、节点数、图深度、图快照字节和总执行耗时配置；默认关闭且写入 `.env.example` 占位值。
- 对外 API 不新增必需字段，不改变现有客户端展示；如暴露诊断摘要，只能是可选、有界且不包含内部查询、对象、授权参数或隐藏推理的字段。
- 自动化验证重点覆盖 Workspace/项目隔离、等价节点判定、无环依赖、确定性顺序、并发上限、失败隔离、取消、恢复、完整性和无写入副作用。
