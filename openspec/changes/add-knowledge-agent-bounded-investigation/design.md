## Context

`add-knowledge-agent-continuous-follow-up` 已把 Knowledge Agent 从无状态问答扩展为持久化对话：服务端先判断继续/新话题/澄清，再用版本化工作集提供检索种子，最终事实仍由当前 Run 重新检索 Entry、读取来源并生成 Evidence。现有 Runner 仍是一条固定单轮执行图，无法在看到首轮结果后判断“还缺什么”并继续补查。

本 change 在现有 Run、Worker、只读工具、Evidence 和 AIProvider 上增加受限调查分支。它面向 Workspace 或项目内较复杂的问题，但必须同时满足：不联网、不写正式知识、不信任模型传入的范围或对象、默认最多三轮、过程可取消/恢复/审计，并让 quick 路径保持现有时延与成本。

## Goals / Non-Goals

**Goals:**

- 为每条消息提供 `auto`、`quick`、`investigate` 三种请求模式，并固化最终选择。
- 让调查模式形成“观察当前证据 → 找出覆盖缺口/冲突 → 提出少量新查询 → 应用执行 → 再观察”的有限循环。
- 用应用层预算、去重和确定性停止规则约束模型，默认最多三轮。
- 持久化调查、轮次、查询和证据账本，使轮询、取消、崩溃恢复和逐轮审计成立。
- 最终答案只引用当前 Run 已核验 Evidence，并明确报告停止原因、未解决缺口和冲突。
- 修复连续追问验收中发现的当前助手占位消息进入历史窗口，以及测试连接未回收警告。

**Non-Goals:**

- 不提供联网搜索、网页抓取、新 Source 创建或 Discovery Agent 协作。
- 不提供 Entry 或目录的新增、修改、移动、删除、合并，也不自动保存回答。
- 不实现客户端界面、流式输出、后台定时研究或离线执行。
- 不建设通用工具调用协议、多 Agent 框架、跨对话长期记忆或自动学习。
- 不允许模型选择 Workspace/项目、任意工具名、预算上限或数据库事务。

## Decisions

### 1. 消息请求模式与实际模式分开保存

消息提交新增 `answer_mode=auto|quick|investigate`，缺省为 `auto`。Run 同时持久化 `requested_answer_mode` 和 `actual_answer_mode`：

- `quick` 直接进入现有单轮执行图；
- `investigate` 直接进入有界调查；
- `auto` 在上下文决策之后调用独立的结构化复杂度路由器，选择 quick 或 investigate；路由不可用、输出非法或超时时显式 fallback 到 quick。

`client_message_id` 的首次提交同时固化回答模式；幂等重试不得用新载荷改变它。上下文模式与回答模式保持正交：前者决定如何理解追问，后者决定要不要多轮补查。

选择独立路由器而不是扩展上下文决策 Agent，是因为二者失败语义和观测目的不同，也便于将 `investigation_route` 单独计费、降级和评测。未选择“auto 一律调查”，以免普通问答不必要地增加成本和等待。

### 2. 应用编排有限循环，模型只给结构化下一步建议

调查控制器每轮接收独立问题、范围/主题摘要、已执行查询、已发现 Entry/Evidence 的紧凑账本、覆盖/缺口/冲突和剩余预算，输出固定结构：

- `action`: `search`、`answer` 或 `insufficient`；
- 当 action 为 search 时，最多三个新的文本查询；
- `coverage`、`gaps`、`conflicts` 与简短理由。

应用校验输出，去除空白和语义等价的重复查询，再按固定的“搜索正式知识 → 读取 Entry → 读取并核验 Source Evidence”工具链执行。控制器不能输出工具名、对象 UUID、范围、预算或事务指令。

未采用模型原生自由 tool loop，因为它难以保证可预测成本、恢复位置和授权边界；也未把所有轮次一次性写入首轮计划，因为后续查询必须真正观察前一轮结果。

### 3. 双层预算与确定性停止

默认预算为最多 3 轮、每轮最多 3 个查询、全 Run 最多 6 个不同查询、30 个不同 Entry、12 条可引用 Evidence；具体数值由服务端设置提供，API 只能读取摘要，客户端和模型不能放大。调查在以下任一条件满足时停止：

- 控制器选择 `answer` 或 `insufficient`；
- 控制器没有给出合法的新查询；
- 一轮搜索没有新增 Entry 或 Evidence；
- 达到轮次、查询、Entry 或 Evidence 预算；
- Run 被取消或执行失败。

停止原因使用稳定枚举，例如 `controller_complete`、`insufficient`、`no_progress`、`max_rounds`、`query_budget`、`entry_budget`、`evidence_budget`、`cancelled`、`failed`。达到上限不是系统错误：若已有证据可回答则生成带未解决缺口的 partial/正常回答，否则返回 insufficient。

采用“模型主动停止 + 应用强制停止”的双层约束；未只依赖模型判断，因为重复查询和成本上限必须确定性可测。

### 4. 用规范化调查表持久化恢复边界

新增等价于以下结构的模型：

- `KnowledgeInvestigation`：Run 一对一，保存目标、请求/实际模式、状态、预算快照、当前轮次、累计计数、停止原因和时间；
- `KnowledgeInvestigationRound`：保存轮次序号、状态、控制器输出的覆盖/缺口/冲突摘要、增量计数和模型调用归属；
- `KnowledgeInvestigationQuery`：保存轮次内顺序、原查询、规范化指纹、执行状态、结果计数与工具调用归属。

表均冗余 `workspace_id`、`user_id`，所有读取仍通过 Run/Conversation 所有权和 Workspace 复验。`(investigation_id, round_number)`、`(investigation_id, normalized_query_hash)` 唯一；SQLite 与 MySQL 均使用普通兼容字段和显式索引。

采用规范化表而不是把全部过程塞进 Run JSON，便于原子提交单轮结果、唯一约束、分页审计和恢复；覆盖/缺口/冲突可保存为有长度上限的 JSON 摘要，因为它们只是 Run 内观察，不是正式知识。

### 5. 账本是当前 Run 的受控派生状态

账本聚合已执行查询、已发现 Entry、已核验 Evidence、不可用对象和控制器的覆盖/缺口/冲突摘要。对象只保存稳定 ID、指纹、短摘要和轮次归属，不复制完整 Attachment、无限 prompt 或完整回答。

每轮新结果进入账本前按 Entry、Source/Attachment 和现有 Evidence 身份去重。已发现集合跨轮次增长，后续 Entry 读取只接受工作集复验种子、用户显式引用或本 Run 任一已完成查询发现的对象。最终综合只接收当前 Run 可引用 Evidence；历史 Run Evidence 和历史助手回答不能进入账本成为事实。

未将账本建成跨 Run 记忆，因为它会模糊证据新鲜度、范围切换和用户删除后的语义。

### 6. 每个完成轮次是一个可恢复检查点

控制器计划、合法查询、工具结果和账本增量按轮次事务提交。Worker 重启后：

1. 校验 Run/Investigation 尚可执行；
2. 从已完成轮次重建已发现集合与剩余预算；
3. 将未完成轮次安全重置或幂等重放；
4. 从下一未完成轮次继续，而不是丢弃已完成调查重新开始。

只读搜索和对象读取可重放；Evidence 创建沿用当前 Run 内幂等去重。最终助手消息、Run/Investigation 终态、活动槽释放和可选输出工作集仍在一个事务提交。

这样比把循环放在一笔长事务中更利于 MySQL 取消可见性和崩溃恢复。代价是中间轮次可被审计但不对用户表现为最终回答。

### 7. 取消、进度与可观测性按轮次展开

Worker 在路由/控制器模型调用前后、每个查询工具批次前后和最终综合前后，通过独立短会话检查取消。取消后保留已提交轮次用于审计，未提交模型/工具结果被丢弃，不生成正常答案或新工作集。

Run 的 `current_step` 扩展为可识别的 `investigation_route`、`round_plan`、`round_search`、`round_evidence`、`synthesize`，并返回当前轮次。模型调用与工具调用增加可选 investigation/round/query 归属；每次继续记录 provider、model、fallback、error 和耗时。路由 fallback 到 quick、控制器非法输出、工具 partial 与预算停止必须在 Run 摘要可识别。

### 8. 最终综合与公开 API

调查完成后只运行一次最终综合，输入为问题、上下文决策、紧凑账本与当前 Run Evidence。响应除现有答案和引用外，增加调查摘要：请求/实际模式、已完成轮数、查询数、停止原因、覆盖项、未解决缺口与冲突提示。

消息提交 API 增加 `answer_mode`；Run 响应提供摘要；另提供按 Run 获取逐轮调查详情的只读接口。所有接口继续对用户、Workspace 与对话所有权返回 404 语义，账本内容实施长度和数量上限。

quick 路径不创建多轮调查记录，只保存实际模式并继续使用现有单轮检索；这样避免为普通问答改变性能特征。

### 9. 先修复连续追问的两个验收遗留

有限历史查询必须同时排除当前 Run 的用户消息与其空助手占位消息，且忽略其他无内容助手占位；测试需通过真实消息提交流程验证窗口不会少取一条有效历史。跨会话取消测试必须显式关闭独立 session/engine 资源，消除 aiosqlite 连接被 GC 回收的警告。

这些作为本 change 的首批任务，避免新路由/控制器在有污染的历史和不稳定并发测试之上扩展。

## Risks / Trade-offs

- [调查增加模型调用、时延和费用] → quick 保持单轮；auto 可显式降级；设置轮次、查询、对象和 Evidence 硬预算并公开实际模式与停止原因。
- [控制器反复生成同义查询] → 对规范化文本建立 Run 内唯一指纹，非法或无新查询立即 `no_progress` 停止。
- [“无新增 Evidence”可能过早停止] → 同时记录新增 Entry 与 Evidence；若新 Entry 因来源不可读而无 Evidence，保留缺口并允许该轮结束后按确定性规则停止，而不是继续盲查。
- [JSON 覆盖/缺口摘要不可强查询] → 它们仅用于展示和下一轮上下文，关键状态、轮次、查询与对象关系采用规范化字段。
- [崩溃发生在外部模型调用后会重复计费] → 在调用前持久化轮次状态并记录调用，恢复时优先复用已提交结果；未提交调用允许有限重试且计入恢复/预算观测。
- [多轮结果可能把无关 Entry 带入工作集] → 只有最终答案实际有效引用的 Entry 才能进入输出工作集，单纯被搜索发现不代表主题成员。
- [调查摘要可能被误解为事实] → 覆盖、缺口和冲突是过程元数据；事实结论继续要求当前 Run Evidence。
- [SQLite 与 MySQL 并发行为不同] → 迁移和唯一约束在两者走查，并延续独立短会话取消测试和真实 MySQL 验证。

## Migration Plan

1. 先修复历史选择和测试连接回收，运行现有连续追问回归。
2. 新增调查、轮次、查询表及 Run 模式/摘要字段；默认兼容旧客户端的 `answer_mode=auto`，历史 Run 的实际模式可为空或按 quick 展示。
3. 实现路由、控制器、账本和有界编排，再扩展 API 与可观测性。
4. 运行 SQLite 全量迁移/回滚/升级与自动测试；在真实 MySQL 验证迁移、唯一约束、轮次提交、跨事务取消和租约恢复。
5. 客户端尚未使用新字段，因此后端部署可先行；出现问题时可配置 auto 始终路由 quick，并保留调查表供审计。

回滚代码时先关闭 investigate 路由并等待活动 Run 终态，再回滚应用；数据库表和可空字段可保留，若必须 downgrade，先确认没有活动调查并按 Alembic 逆迁移删除。

## Open Questions

无阻塞实施的问题。默认预算先按本设计落地，并由服务端配置与测试固定；真实使用数据积累后再通过独立 change 调整，不在本 change 引入自动学习。
