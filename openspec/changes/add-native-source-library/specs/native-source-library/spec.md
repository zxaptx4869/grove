## ADDED Requirements

### Requirement: 最近收集列表与筛选

收集入口页 MUST 在三个采集入口之外同时承载「最近收集」列表，MUST NOT 新增独立的「全部来源」页。列表 MUST 通过 `GET /api/sources` 携带 `limit=20` 取最近 20 条并按创建时间倒序，MUST NOT 实现分页浏览。采集提交结束回到入口页时 MUST 立即重新查询，使刚提交的来源立刻出现在列表里。列表上方 MUST 提供「全部 / 未归属」两态轻量文字筛选，切换 MUST 重新查询（未归属态 MUST 携带 `unassigned=true`），MUST NOT 提供搜索、状态筛选或批量操作。向下拉动列表 MUST 重新查询并保留当前筛选。

#### Scenario: 入口页同时承载采集与列表
- **WHEN** 用户进入收集栏目
- **THEN** 页面显示三个采集入口与下方的「最近收集」列表，两者同页，不跳转到单独的来源页

#### Scenario: 默认展示全部
- **WHEN** 用户首次进入收集栏目
- **THEN** 筛选为「全部」，列表按创建时间倒序显示最近 20 条来源

#### Scenario: 切换未归属
- **WHEN** 用户把筛选切到「未归属」
- **THEN** 系统携带 `unassigned=true` 重新查询，只显示未归属来源

#### Scenario: 采集结束回到列表
- **WHEN** 用户完成一次采集并从提交结果回到收集列表
- **THEN** 系统立即重新查询，刚提交的来源出现在「最近收集」里

#### Scenario: 下拉刷新
- **WHEN** 用户下拉刷新列表
- **THEN** 系统按当前筛选重新查询，列表内容与状态徽标随之更新

### Requirement: 列表条目与状态呈现

列表每行 MUST 显示类型（图片 / 文字）、标题、附件摘要（文字来源为「文字」，图片来源为「N 张图片」）、创建时间、状态徽标与项目归属标签（未归属或项目名）；状态徽标 MUST 覆盖等待处理、处理中、提取完成与处理失败四种状态。列表 MUST NOT 展示来源的补充说明（`note`），补充说明只出现在详情元信息里。动态标题、徽标与失败文案 MUST NOT 造成行内容横向溢出。

#### Scenario: 图片行
- **WHEN** 列表包含一条多图来源
- **THEN** 该行显示图片类型、标题、「N 张图片」与创建时间

#### Scenario: 文字行
- **WHEN** 列表包含一条文字来源
- **THEN** 该行显示文字类型、标题、「文字」与创建时间

#### Scenario: 补充说明不进列表
- **WHEN** 来源填写了补充说明
- **THEN** 列表行不显示该说明，进入详情后在元信息里可见

#### Scenario: 归属标签
- **WHEN** 来源未归属项目
- **THEN** 该行显示「未归属」标签；已归属时显示项目名

### Requirement: 列表 done 副状态

列表 MUST 依据 `SourceOut` 的现有计数派生 `done` 副状态并遵守以下优先级：`pending_candidate_count > 0` 且 `evidence_entry_count == 0` 显示「待确认 N 条」；`pending_candidate_count > 0` 且 `evidence_entry_count > 0` 显示「部分确认 · N 条正式知识」；`pending_candidate_count == 0` 且 `evidence_entry_count > 0` 显示「N 条正式知识」；两者都为 0 显示「还没有候选」。主状态不是 `done` 时 MUST NOT 显示副状态。

#### Scenario: 待确认
- **WHEN** 来源已提取完成、有 2 条待确认候选且没有正式知识
- **THEN** 该行副状态显示「待确认 2 条」

#### Scenario: 部分确认
- **WHEN** 来源已提取完成、有 1 条待确认候选且已产生 1 条正式知识
- **THEN** 该行副状态显示「部分确认 · 1 条正式知识」

#### Scenario: 全部确认
- **WHEN** 来源已提取完成、没有待确认候选且已产生 3 条正式知识
- **THEN** 该行副状态显示「3 条正式知识」

#### Scenario: 没有候选
- **WHEN** 来源已提取完成、既没有待确认候选也没有正式知识
- **THEN** 该行副状态显示「还没有候选」

#### Scenario: 非完成态不显示副状态
- **WHEN** 来源处于等待处理、处理中或处理失败
- **THEN** 该行只显示状态徽标，不显示 `done` 副状态

### Requirement: 处理失败与处理未启动的重试

处理失败的来源 MUST 在行内展示服务端 `failure_reason` 原文并提供「重试」入口，点击 MUST 调用 `POST /api/sources/{id}/process` 并在成功后刷新该来源状态。`status` 为等待处理且 `has_processing_task` 为 false 的来源 MUST 显示「处理未启动」并提供「重试处理」，点击同样调用该端点；系统 MUST NOT 使用「等待超过 N 秒」等时间阈值启发式判断未启动。处理中与已完成的来源 MUST NOT 提供重复触发入口，服务端 409 MUST 视为状态本身正常、MUST NOT 提示为失败。

#### Scenario: 失败来源重试
- **WHEN** 用户在列表点击失败来源的「重试」
- **THEN** 系统调用处理端点，该来源状态复位并重新进入等待处理

#### Scenario: 等待处理但没有任务
- **WHEN** 来源状态为等待处理且 `has_processing_task` 为 false
- **THEN** 该行显示「处理未启动」与可点的「重试处理」

#### Scenario: 重复触发被服务端拒绝
- **WHEN** 重试时服务端返回 409（来源正在处理或已完成）
- **THEN** 系统不把它当作失败提示，只刷新该来源状态

#### Scenario: 不用时间阈值猜测
- **WHEN** 来源等待处理的时长较长但仍有处理任务
- **THEN** 系统不显示「处理未启动」，只显示「等待处理」

### Requirement: 列表加载、空与失败状态

列表 MUST 明确区分加载中、空与加载失败三种状态：加载中 MUST 保留已有内容或稳定占位，不闪空白；空列表 MUST 说明当前状态并只给出一个最相关的采集动作；加载失败 MUST 说明问题与下一步，并提供「重新加载」入口，MUST NOT 展示堆栈或静默失败。

#### Scenario: 列表为空
- **WHEN** 当前筛选下没有任何来源
- **THEN** 列表区显示「还没有来源」说明与一个采集动作入口

#### Scenario: 列表加载失败
- **WHEN** 列表请求因网络原因失败
- **THEN** 列表区显示失败说明与「重新加载」，点击后重新查询

#### Scenario: 刷新中不闪空
- **WHEN** 用户下拉刷新且列表已有内容
- **THEN** 原有条目保持可见，不出现空白闪烁或布局跳动

### Requirement: 只读来源详情

系统 MUST 提供来源详情的只读视图，读取 `GET /api/sources/{id}` 与 `GET /api/sources/{id}/candidates`，并展示：元信息（类型、创建时间、项目归属、补充说明，未归属与未填写 MUST 有明确文案）、原始材料（图片网格并支持放大查看，文字来源显示正文）、OCR 文本（图片无 OCR 时说明原因）与 AI 候选列表（MUST 标注为候选且未应用，含目录建议与理由）。图片 MUST 通过 `GET /api/sources/{id}/attachments/{attachment_id}/file` 携带认证读取；读取 MUST 走带认证头的下载通道并落到本地缓存后再渲染，MUST NOT 依赖图片组件自带的请求头（Expo Go 下该请求头不会发出，附件端点会收到 401）。单张图片读取失败 MUST 在图片位置给出失败提示与重试入口，MUST NOT 静默留白，其余详情内容 MUST 仍可阅读。详情 MUST NOT 提供候选的确认、拒绝、写入或归档入口，MUST NOT 展示 `recommended_project_id` 与 `project_recommendation_reason`。

放大查看 MUST 使用浅色背景（MUST NOT 用近黑底），MUST 支持双指捏合缩放与放大后的拖动平移，并提供双击放大 / 还原与可见的操作提示。图片 MUST 按视口宽度铺满渲染并保持长宽比，使长截图放大后仍接近原图清晰度；内容超出视口时 MUST 可拖动，起始位置对齐图片顶部。切换图片 MUST 复位缩放与位移。

#### Scenario: 查看图片来源详情
- **WHEN** 用户点开一条图片来源
- **THEN** 详情显示元信息、图片网格、OCR 文本与候选列表，点图片可放大查看

#### Scenario: 放大查看长截图
- **WHEN** 用户点开一张长截图并双指放大，随后拖动
- **THEN** 图片在浅色背景上按宽度铺满显示，可继续放大并拖动看到局部细节，关闭后回到详情

#### Scenario: 查看文字来源详情
- **WHEN** 用户点开一条文字来源
- **THEN** 详情显示元信息、文字正文、OCR 区域的说明文案与候选列表

#### Scenario: 图片读取失败可重试
- **WHEN** 原始材料中的某张图片读取失败
- **THEN** 该图片位置显示失败提示与重试入口，详情其余内容仍可阅读，重试成功后显示图片

#### Scenario: 候选只读
- **WHEN** 用户浏览详情里的 AI 候选
- **THEN** 只看到候选内容、目录建议与理由，没有任何确认、拒绝、写入或归档入口

### Requirement: 改归属

详情 MUST 通过 `GET /api/projects` 提供「未归属」与全部项目作为目标选项。选择目标 MUST 只更新界面选择态，MUST NOT 立即提交；MUST 由用户点「确认修改」后才提交 `PATCH /api/sources/{id}`（`project_id`）。选择的目标与当前归属相同时确认入口 MUST 不可用且 MUST NOT 发起请求。提交进行中 MUST 显示加载状态与「正在更换项目并重新推荐目录」的用户可读说明（MUST NOT 暴露「路由」等实现术语）、禁用项目选项与两个按钮，并 MUST NOT 允许重复提交。打开操作前 MUST 先用 `project_locked` 与处理状态预判：已被正式知识引用 MUST 只显示阻断说明（提示先到桌面工作台处理关联的正式知识），处理中 MUST 只显示阻断说明（等处理结束后再改），两种情况 MUST NOT 渲染项目列表。预判未命中时服务端 409 MUST 作为兜底并原样透传文案。提交成功后 MUST 关闭弹层并更新详情与列表的归属；失败 MUST 保留弹层并原样展示服务端文案。行为信号由后端记录，客户端 MUST NOT 额外上报。

#### Scenario: 选择后需确认再提交
- **WHEN** 用户在弹层里点了另一个项目但未点「确认修改」
- **THEN** 系统只更新选择态（选项标记随之改变），不发起任何写请求，弹层保持打开

#### Scenario: 确认后才提交
- **WHEN** 用户点「确认修改」
- **THEN** 系统提交所选 `project_id`，成功后关闭弹层并在详情与列表显示新归属

#### Scenario: 选择当前归属时确认不可用
- **WHEN** 用户选择的目标与当前归属相同
- **THEN** 确认入口不可用，不发起请求

#### Scenario: 提交中显示加载状态
- **WHEN** 改归属请求正在进行
- **THEN** 确认入口与弹层显示进行中的加载状态，项目选项不可切换，取消入口不可用，重复点击不会再次提交

#### Scenario: 锁定来源的预判
- **WHEN** 用户对 `project_locked` 为 true 的来源点击「改归属」
- **THEN** 系统只显示阻断说明与关闭入口，不渲染项目列表

#### Scenario: 处理中来源的预判
- **WHEN** 用户对处理中的来源点击「改归属」
- **THEN** 系统说明等处理结束后再改，不渲染项目列表

#### Scenario: 服务端 409 兜底
- **WHEN** 预判未命中但服务端返回 409
- **THEN** 系统在弹层里原样展示服务端文案，保留弹层与当前选择，不执行修改

#### Scenario: 更换项目中的状态
- **WHEN** 改归属请求正在进行
- **THEN** 该来源显示「更换项目中」状态，完成后消失；弹层内说明正在更换项目并重新推荐目录，不出现「路由」这类实现术语

### Requirement: 删除

删除 MUST 提交 `DELETE /api/sources/{id}`。处理中与已被正式知识引用两类 MUST 由服务端 409 阻止，界面 MUST 原样展示服务端文案并 MUST NOT 执行删除。存在待确认候选（`pending_candidate_count > 0`）时后端放行，界面 MUST 二次确认并在确认文案里说明「将一并移除这些候选」；没有待确认候选时确认文案 MUST 说明原始材料与已生成的候选都会移除且无法恢复。删除成功后 MUST 关闭详情、回到列表并刷新；删除失败 MUST 保留详情并原样展示服务端文案。

#### Scenario: 处理中被阻止
- **WHEN** 用户删除处理中的来源
- **THEN** 系统展示服务端 409 文案，不执行删除

#### Scenario: 已被引用被阻止
- **WHEN** 用户删除已被正式知识引用的来源
- **THEN** 系统展示服务端 409 文案，并说明需先处理关联的正式知识

#### Scenario: 有待确认候选的二次确认
- **WHEN** 用户删除一条有 N 条待确认候选的来源
- **THEN** 系统在确认文案里说明将一并移除这 N 条候选，用户确认后才删除

#### Scenario: 删除成功后回到列表
- **WHEN** 删除成功
- **THEN** 详情关闭，列表刷新且不再包含该来源

### Requirement: 前台轮询

系统 MUST 复用既有 `useAppStateActive` 判定前台，并只在**前台且列表存在等待处理或处理中的条目**时轮询来源列表；列表中不再有这类条目时 MUST 停止轮询。进入后台 MUST 停止请求；回到前台 MUST 立即查询一次再决定是否继续。轮询 MUST NOT 展示百分比进度，间隔 MUST 在 `design.md` 记录并说明依据。

#### Scenario: 有活动条目才轮询
- **WHEN** 列表中存在等待处理或处理中的来源且 App 在前台
- **THEN** 系统按记录的间隔轮询来源列表

#### Scenario: 全部结束即停止
- **WHEN** 列表中所有来源都已是提取完成或处理失败
- **THEN** 系统停止轮询，不再发起定时请求

#### Scenario: 后台停止与前台恢复
- **WHEN** App 进入后台再回到前台
- **THEN** 后台期间不发请求，回前台立即查询一次，再根据是否仍有活动条目决定是否继续轮询

### Requirement: 列表与详情的错误处理

列表与详情的请求失败 MUST 分别给出可重试的提示，MUST NOT 静默失败。后端 4xx 文案（如处理中、已被引用等）MUST 原样透传，MUST NOT 自造替代文案。详情读取失败 MUST 保留在详情层内提示并可重试，MUST NOT 直接关闭详情丢失上下文。

#### Scenario: 详情加载失败
- **WHEN** 详情或候选请求因网络原因失败
- **THEN** 详情层内显示失败提示与重试入口，不自动关闭详情

#### Scenario: 后端文案原样透传
- **WHEN** 服务端返回带 `detail` 的 4xx 响应
- **THEN** 界面显示该文案原文，不使用客户端自造文案替换
