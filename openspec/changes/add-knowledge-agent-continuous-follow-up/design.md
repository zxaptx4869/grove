## Context

`add-knowledge-agent-foundation` 已建立持久化对话、单会话串行 Run、可信只读工具和本 Run Evidence，但执行器刻意把每个问题独立处理。当前消息“它为什么更适合？”不会携带“它”指向的主题，直接检索通常召回不足；反过来，如果把整段聊天直接拼进模型 prompt，历史助手回答又可能被误当成正式事实，并造成上下文膨胀和主题串扰。

原生 App 以对话为默认首页，Web 也将迁移到同一知识 Agent API。客户端正式接入前，需要先把“连续”定义成稳定的后端领域能力：系统明确判断本轮与上一主题的关系，用结构化工作集保存可复验的正式 Entry 标识，并让用户能覆盖错误判断。

基础 change 验收还发现三项应在继续扩展前硬化的实现缺口：全部 Evidence 句柄失效时回答仍可能为 `completed`；工具空结果/error 的 fallback 汇总语义错误；执行中的 `current_step` 与取消检查使用长事务，前者不能被轮询及时看到，后者在 MySQL `REPEATABLE READ` 下可能看不到其他事务的新取消请求。这些不改变现有产品规格，但会作为本 change 的前置修复。

## Goals / Non-Goals

**Goals:**

- 自动区分继续追问、新话题和需要澄清，并允许用户显式覆盖。
- 把省略或指代问题改写成可独立检索的查询，同时让决策对客户端可见。
- 以版本化工作集保存当前主题涉及的正式 Entry 标识，而不是保存 AI 回答事实。
- 合并工作集种子与本轮新召回，并对范围、Entry 与 Source Evidence 全部重新校验。
- 保持固定、有预算的执行图、单会话串行、取消、恢复和逐阶段可观测性。
- 修复基础验收发现的引用降级、工具降级汇总和运行中状态可见性问题。

**Non-Goals:**

- 不实现客户端 UI、流式回复、消息引用手势、推送或离线对话。
- 不建设整段对话摘要、长期个人记忆、跨对话记忆或用户画像。
- 不实现模型自由规划工具、多轮研究循环、联网搜索或多 Agent 协商。
- 不新增任何知识写工具，不改变 Candidate/Draft 与用户确认边界。
- 不跨范围复用工作集，不把历史 Evidence 直接作为新 Run 引用。

## Decisions

### 1. 每条消息显式携带上下文模式，自动判断可以被用户覆盖

消息提交新增 `context_mode`：

- `auto`（默认）：由上下文决策 Agent 判断 `continue`、`new_topic` 或 `clarify`。
- `continue`：用户明确要求沿用当前主题；决策 Agent 只能补全独立查询，不能改判为新话题。
- `new_topic`：用户明确切断旧上下文，直接把当前消息作为新检索起点，不调用关系分类。

Run 保存请求模式、最终动作、主题标签、独立检索查询、输入工作集版本、用于判断的消息 ID、provider/model/fallback/error。客户端以后可显示“继续基于：闭水试验”或提供“按新话题重试”，而不是让上下文选择成为不可见的模型猜测。

`new_topic` 是用户的确定性命令：提交事务立即关闭当前活动工作集，即使后续 Run 取消或失败也不自动恢复旧主题。`continue` 在没有活动工作集时返回澄清，不猜测历史主题。

备选方案：完全自动且不暴露模式。它更简洁，但误判后用户无法纠正，也难以解释 Agent 为什么引用上一轮对象，因此不采用。

### 2. 上下文决策只读取有限历史，历史回答只用于语言消歧

决策 Agent 输入当前消息、活动主题标签、工作集 Entry 标题，以及对话中最近有限条用户/助手消息。历史窗口由配置控制（默认 8 条），每条内容截断；保存用于本轮判断的消息 ID，不持久化原始 prompt。

结构化输出为：动作、`standalone_query`、简短 `topic_label`、可选澄清问题和理由。应用层进行归一化：

- 独立查询为空时回退到当前用户消息；
- `continue` 但没有活动工作集时改为 `clarify`；
- `clarify` 没有有效问题时使用确定性澄清文案；
- `auto` 分类模型不可用时安全降级为 `new_topic`，不偷偷携带旧上下文；
- 强制 `continue` 的改写模型不可用时用“主题标签 + 当前消息”形成确定性查询并标记降级。

历史助手消息只能帮助解析“它”“上一个方案”等语言指代，不能直接进入回答事实上下文。回答组织器仍只接收本轮重新读取的 Entry 和 Evidence。

备选方案：把最近 N 轮完整消息直接交给回答模型。实现虽快，却无法阻止历史幻觉固化、token 随轮次增长和主题串扰，因此不采用。

### 3. 使用版本化显式工作集，不在 Conversation 上维护可变 JSON

新增：

- `KnowledgeContextVersion`：归属 conversation/user/workspace，含递增版本号、父版本、来源 Run、范围快照、主题标签、状态与活动槽。
- `KnowledgeWorkingSetItem`：归属一个 context version，保存可空 `entry_id`、Entry/Project/目录标题快照、来源 Run、纳入原因、排序与最近使用时间，不保存 Entry 正文或助手回答。

同一对话最多一个活动 context version，继续使用 `(conversation_id, active_slot)` + 终态 NULL 的 SQLite/MySQL 兼容约束。Run 保存 `input_context_version_id` 与 `output_context_version_id`，从领取开始就固定输入版本，恢复执行不会漂移到后来状态。

工作集默认最多 15 条，与回答上下文预算一致。`continue` 成功时以旧工作集与本轮有效引用 Entry 的并集生成新版本，优先保留本轮引用和最近使用项；`new_topic` 结束时用新主题替换旧版本，只有有效引用 Entry 才生成 item，知识不足时允许保留一个零 item 的主题版本，使下一句省略追问仍能理解话题。旧版本变为 superseded，但保留审计。范围切换关闭活动版本。

备选方案：在 conversation 上存一个不断覆盖的 Entry ID JSON。它迁移简单，但无法解释某个历史 Run 使用了哪个集合，也不利于崩溃恢复和范围审计，因此不采用。

### 4. 工作集只提供候选种子，每轮仍做新检索和重新核验

对 `continue` Run：

1. 从固化输入工作集加载 Entry 种子；
2. 重新校验 Entry 仍存在、属于 Run 范围且为正式知识；
3. 用独立查询执行新一轮混合召回；
4. 合并种子与新召回并统一重排、截断；
5. 重新读取 Entry 与 Source/Attachment，生成本 Run 新 Evidence。

历史 Evidence 句柄不能直接用于新回答。这样来源变化、Entry 移动或删除会在当前 Run 被发现；历史上下文只提高召回稳定性，不降低证据可信度。

工作集 Entry 成为“已发现集合”的一种服务端可信来源，与本轮搜索结果和未来用户显式引用并列。模型仍不能凭 UUID 扩张对象集合。

备选方案：直接复用上一轮 Evidence 或只检索工作集。前者可能引用已变化来源，后者无法回答“还有别的吗”等扩展追问，因此不采用。

### 5. 固定执行图增加上下文分支，但不升级为开放式 Agent 循环

新执行图：

```text
上下文决策
  ├─ clarify → 写澄清回复，不搜索、不更新工作集
  └─ continue/new_topic
       → 加载并复验种子
       → 新检索 + 合并重排
       → 读 Entry → 读新 Evidence
       → 组织回答 → 校验引用
       → 原子提交回答与新工作集版本
```

上下文决策最多一次模型调用；检索、Entry、Evidence 和回答预算沿用基础 change。澄清回复属于对话控制信息，`answer.status=clarification`、无引用、Run 为正常终态，不作为知识回答也不更新工作集。

备选方案：让模型根据历史自由决定是否搜索、搜索几次。连续追问尚未形成真实评估数据时，这会同时放大成本、恢复和可信边界，因此留到受限调查 change。

### 6. 工作集只由有效 Evidence 支持的结果推进

最终引用校验额外返回请求句柄数、有效句柄数和被丢弃数。出现以下情况时：

- 有事实性回答但有效引用为零：回答改为 `insufficient`，Run 至少为 `partial`；
- 部分句柄失效：保留有效引用，回答与 Run 标记 `partial`，并在可观测摘要记录；
- 模型明确给出纯澄清：允许无引用且不推进上下文；
- 知识不足：不得把召回项写成工作集 item；`continue` 保持输入版本，`new_topic` 可建立只含主题标签的空版本；
- 取消、失败：不推进上下文；回答模型 fallback 不得添加工作集 item，新话题是否保留空主题按已确定的上下文决策处理。

只有本轮最终有效引用涉及的 Entry 才进入输出工作集 item。模型召回但未引用的 Entry 不会长期污染主题；主题标签属于对话导航信息，不被当作正式知识。

备选方案：把所有召回结果都加入工作集。它容易在多轮后积累不相关 Entry，造成“记忆越用越脏”，因此不采用。

### 7. 运行中步骤与取消状态通过短事务读写

现有执行器在一个长事务里修改 `current_step`，外部轮询只能看到领取时的 `claim`；同一事务内反复查询取消状态，在 MySQL 默认隔离级别下也可能看不到其他会话刚提交的取消。

新增独立的短会话辅助函数：每个步骤开始前用短事务更新 `current_step`，取消检查也用新的短会话读取最新状态。主执行会话不再把中间步骤标记为脏字段，最终回答、Run 终态与输出工作集仍在一个事务提交。这样不暴露半成品回答，同时让进度与取消跨 SQLite/MySQL 可见。

备选方案：每个工具阶段都提交主事务。它会把半成品 Evidence、回答和工作集暴露给恢复逻辑，原子边界更复杂，因此仅把运行控制状态放入短事务。

### 8. 降级汇总区分“空结果”与“异常/部分失败”

模型调用仍用 `is_fallback`。工具状态按确定性规则聚合：`ok` 与正常 `empty` 不算 fallback；`partial`、`denied`、`unavailable` 和 `error` 进入受影响阶段，其中 `error` 必须明确带错误。上下文决策作为新的模型 purpose 单独记录。

这修复当前 `status != TOOL_ERROR` 导致 empty 被误报、error 反而不计入汇总的问题。API 字段暂沿用 `fallback_summary` 兼容现有客户端，但阶段内容表达的是总体降级/异常。

## Risks / Trade-offs

- [分类误把新话题当追问] → 返回决策与主题标签，支持 `new_topic` 覆盖；自动分类 fallback 默认不携带旧上下文。
- [分类误把追问当新话题] → 用户可用 `continue` 重试；保留近期消息 ID 与分类元数据用于评估。
- [工作集逐轮污染] → 只纳入最终有效引用 Entry、统一重排、设置上限并版本化，未引用召回项不保留。
- [历史 Entry 已删除或移出范围] → 每轮重新校验并记录不可用，不复用历史 Evidence。
- [增加一次分类模型调用带来延迟和成本] → `new_topic` 直接绕过；分类上下文严格限长，后续根据真实数据评估规则短路。
- [短事务进度更新与主执行终态竞争] → 所有更新带活动状态条件；终态提交后短事务不得再写步骤。
- [数据表增长] → 工作集只有标识与短快照，单版本有上限；长期保留与压缩仍由后续运维 change 决定。

## Migration Plan

1. 先修复 Evidence 全失效降级、工具汇总和独立短事务进度/取消，并补 SQLite 与 MySQL 行为测试。
2. 新增上下文版本、工作集表和 Run 上下文字段；既有对话没有活动工作集，第一条新消息按 `new_topic` 处理，不回填历史推断。
3. 实现上下文决策 Agent、结构归一化与有限历史读取；增加 provider/model/fallback 记录。
4. 扩展工具上下文、合并重排和固定执行图，最后原子写回答与输出工作集。
5. 扩展 API schemas 与手动走查，保持旧客户端不传 `context_mode` 时默认为 `auto`。
6. 完整验证后再由后续 Web/App change 接入可视化连续对话。

回滚时先停用新上下文决策路径，使所有消息按 `new_topic` 走基础执行图；新增表和可空 Run 字段可保留，不影响旧对话与旧 Reader。若回滚迁移，只能在确认没有客户端依赖上下文元数据后删除新增表/列。

## Open Questions

- 自动分类准确率达到何种水平后适合增加确定性规则短路，需要客户端接入后的真实追问样本评估；本 change 不预设阈值。
- 工作集是否需要在客户端展示和手动移除单个 Entry，留到 Web/App 交互 change 决定；后端首版只返回主题和版本摘要。
- 跨对话复用主题或“固定记住某条知识”属于长期记忆产品设计，不从连续追问自动推导。
