## Context

问题证据、用户目标及涉及能力见 proposal 和多轮基线。首轮实现已解除上下文理解与事实工作集的绑定，并补齐项目子集与分组；2026-09-06 用户手动测试进一步暴露条件误继承和项目实体误判。本次沿用同一 change 修订任务衔接设计，不把未通过的原生验收视为完成。

本修订已获用户确认，任务状态实现和确定性验证已完成，真实对照及原生验收状态见 `docs/验收记录/knowledge-agent-task-state-2026-09-06.md`。首轮历史自动评测见 `docs/验收记录/knowledge-agent-multiturn-fix-2026-09-06.md`，不能作为本修订的验证结果。

## Goals / Non-Goals

目标是同一对话自然完成总数、分组、条件调整、对象查阅与通用讨论。修订先在只读查询任务上验证条件替换、撤销、深入与恢复，其他分支保持语义边界和兼容；不实现任意任务图或统一所有回答规划器。正式 Entry、Source、Candidate 与目录仍不由本次只读链路修改；其他非目标见 proposal。

## Decisions

1. **复用 Run 保存有界任务版本，独立于事实工作集。** 不新增全局可变会话表；明确区分同范围内的自动任务切换和用户显式重置。任务可作为意图线索被恢复，但历史答案与 Evidence 不因此成为本轮事实。具体状态、边界与落盘规则见下文。
2. **任务选择与条件解析各自只承担一个职责。** 上下文模型选择从哪个任务继续，查询规划器根据原始消息和所选状态解释条件变化，服务端完成确定性归并。保留开放讨论、结果路由和现有执行器；不以合并所有模型调用为目标。澄清只用于影响执行的必要歧义，对象指代继续绑定实际展示快照。
3. **项目名称是筛选条件，不是授权。** EntrySet 增加可选有界 project_name；服务端先在可信 Workspace/项目范围精确解析唯一名称，并在查询与聚合中强制追加同一项目谓词。找不到/重名/越界时不删除条件、不回退全空间。已有 schema 保留版本并增加可选字段，所有模型输入仍拒绝 id 和未知字段。执行快照记录实际筛选项目；恢复及共享图指纹包含该条件。
4. **项目分组返回有标识的桶。** project 分组以项目 id 为键、名称为可选 label，使用限定范围的项目集合左连接匹配 Entry，返回零条项目。保留桶数、结果字节、完整性和排序边界，SQLite/MySQL 使用一致语义。客户端显示服务端 label，旧维度照常展示。
5. **依据限制与回退一致。** 修正规则对通用知识的过宽匹配；明确禁止 Grove 的请求不进入检索兼容分支，纯模型回答保留正常依据与可观测性。用户仅用个人知识库的限制继续有效；不以消除 fallback 为目的忽略非法计划。
6. **评测继续核对真实任务。** 不改写场景来掩盖产品缺陷，统计核对值、完整性及实际范围；新增字段只增加评测识别能力。对新对象指代和开放解释用真实响应人工复核，自动通过不替代原生用户走查。

### 1. 当前缺口与最小调用调整

现有 `dialogue_context.py` 装配近期消息和最近集合，遇到任何 `new_topic` 截断；`knowledge_context.py` 用“保留未变条件”生成 `standalone_query`。`runner.py` 将该句交给结果路由，`structured_entry_search.py` 再仅用该句生成查询计划。Run 369 把“新疆旅行”写成语义条件，Run 370 继续继承，SQL 因而正确执行了错误任务。

目标调用链如下；各箭头是职责边界，不表示新增一次模型调用：

```text
原始消息 + 当前授权范围 + 有界任务/原始对话
  -> 上下文决策：选择、创建、深入、恢复任务或具体澄清
  -> 服务端：核验任务句柄，核实有界项目名称候选
  -> 既有结果路由：仅决定 answer / entries，读取同一份上下文
  -> entries 查询规划：原始消息 + 选定任务 + 项目候选 -> 条件变更、输出
  -> 服务端归并并固化 EntrySetSpec / StructuredQueryPlan
  -> 既有只读执行器 -> 结果及有效任务版本
```

- 上下文决策不生成最终查询过滤器；它返回任务关系、选定基线、待澄清项、对象指代与摘要。独立问题仍供展示和旧路径使用，不能覆盖原始消息。
- 查询规划是本轮结构化条件的唯一语义解释阶段；返回有来源的条件增量和输出变化，由服务端编译为已有规范化计划，不同时要求模型生成第二份完整集合。若项目核实后才发现歧义，该阶段也可返回未决问题，服务端终止本轮查询并保存待澄清状态，不强行生成计划。
- 结果路由不修改任务筛选。`answer` 的复合计划仍负责其回答义务和多个数据请求，接收原始消息与选定任务上下文；旧的改写句不是唯一依据。本修订不统一所有复合子请求为一个集合。
- 不在三次现有模型调用之外增加常驻“检查 Agent”；保留模型调用和阶段级耗时审计，以真实对照衡量成本。

### 2. 最小任务状态

任务是会话内的意图与查询控制信息，不是产品的采集 Task、正式 Entry 或事实工作集。新增内部 `dialogue_task_v1` 协议，使用 Pydantic 校验。任务及版本句柄由服务端产生，模型只能选择本轮提供的句柄。

| 状态 | 内容与来源 | 生命周期 |
|---|---|---|
| 授权边界与 epoch | owner、Workspace、界面范围、最近显式重置消息，由服务端注入 | 模型不得改变；切换范围或显式新话题使旧任务不可继承 |
| 任务目标与关系 | 查询或讨论的简短目标、任务句柄、可选父任务/基线版本 | 支持继续、深入和恢复；不根据每个完整句子机械新建任务 |
| 当前关注对象 | 近期提到的项目或 Entry 线索、来源消息 | 只用于理解，不能自动转成查询谓词 |
| 查询状态 | 规范化集合、输出种类、列表排序及数量 | 从选定版本继承，经明确增量修改；空值表示无此限制 |
| 条件来源 | 每项条件对应的用户消息片段或既有条件版本；显式、继承、推断标记 | 推断不得在后续轮次冒充用户明确要求；撤销保留变更记录 |
| 依据限制 | 当前任务“不查 Grove”等限制及来源 | 与任务绑定；恢复时重新合并本轮限制和界面覆盖 |
| 待澄清与最近结果 | 未决问题、待选任务/条件；真实结果 Run 和有序列表句柄 | 澄清不产生已执行集合；结果缺失、过期或越界时不换对象 |

第一版保留一个活动任务和最多四个近期任务，父关系深度最多二层；始终优先保留活动任务及可恢复父版本，其他按最近使用裁剪。历史条数、单条长度沿用现有配置，任务和实体上下文另设字节上限并记录裁剪。超过边界时只说明缺少哪段任务，不搜索全会话或伪造旧条件。开放讨论只需目标、原始对话与依据限制，查询字段可空。

### 3. 条件变化与任务边界

- 任务选择使用 `start / continue / branch / resume / clarify` 五种内部操作；`branch` 从已有版本深入，`resume` 选择已有任务版本。更正和撤销通过同一条件增量表达，不新增对应题型路由。
- 查询条件用白名单字段的 `set / clear` 表达，未出现的字段继承所选基线；同一字段只允许一次操作。start 从无筛选基线开始；branch 从指定版本派生且不覆盖父版本；continue 更新本任务；resume 先恢复指定版本再应用增量。输出、排序和数量同样明确继承、替换或重置，不把“改为参数”解释成方法与参数的交集。
- 每个变化带当前消息片段/服务端提供的消息句柄，继承项带原版本来源。服务端校验句柄、字段、类型和来源存在性；语言片段是否充分支持该变化仍是模型判断，不能宣称 schema 校验可证明语义正确。
- `resume` 恢复目标任务的查询条件，不复用其历史数字；随后应用当前消息的修改。目标不在有界候选中时具体澄清。选择之前更宽的任务属于待校验的范围变化，不能用“继续”标签暗中删除条件。
- 用户界面 `new_topic`、自然语言明确要求丢弃此前上下文、scope_change 是硬边界。普通自动 `new_topic` 只让旧任务不参与本轮执行，可以保留有界任务描述供日后选择；不得自动继承旧筛选或用户陈述。
- 外部 `continue / new_topic / clarify` 枚举保留。内部 `branch / resume` 映射为 `continue`，`start` 映射为 `new_topic`；显式 `continue` 不允许模型暗中切成无关任务，必要时澄清。模型判断失败不创建硬重置边界。
- 本轮事实工作集不因任务池增加而扩大。恢复只读查询后重新查库；恢复讨论只选该任务关联的合法用户陈述，历史助手文本始终仅供意图理解。

例如“总量 -> 房子装修 -> 新疆旅行 -> 分项目”应保留总量任务和项目查看之间的关系。最后一句由原始上下文判断恢复汇总还是细分当前集合；没有“出现分项目就清空项目”的固定规则，也不能因为当前只有一个项目就认定分组无意义。明确“全部项目分别统计”必须回到授权范围内的全项目集合；明确“这些旅行相关结果分项目”必须保留语义条件。

### 4. 项目核实与歧义策略

上下文输入提供当前范围及近期任务中已核实的项目名称。上下文模型可提出最多五个、确实出现在所提供用户消息中的名称片段；服务端在固定权限内批量精确查找项目，并把匹配名称、重名/未找到状态交给查询规划器。候选解析只读取项目元数据，不读取 Entry、计数或 Source，保留调用摘要和耗时；不把所有项目或原始知识装入提示词，不新增自由工具循环。

项目存在是判断依据，不能直接证明用户是在限定该项目。“新疆旅行有多少条”结合项目统计任务可解析成项目条件；“关于新疆旅行的内容”仍可能是主题搜索。未知或重名且影响执行时具体澄清；不得静默改成全 Workspace 或语义搜索来绕过项目问题。已明确的主题查询不因存在同名项目被强制改为项目查询。

已核实项目的内部绑定由服务端记录真实项目标识，模型仍只接收名称或受限句柄。恢复时验证该绑定的当前权限与名称变化；原项目删除后新建同名项目不能悄悄替代旧目标。缺少绑定的 legacy 基线只能作为待核实名称线索，不能宣称恢复了同一个实体。

明确的原始请求和已选界面约束优先。存在两个会显著改变统计集合、且上下文不足以区分的解释时，只询问差异，例如“统计全部项目，还是只统计刚才旅行相关的结果？”，保存未决任务以便下一句直接补全；不靠模型自报置信度阈值决定是否执行。可明确执行时直接回答，并让既有集合摘要及助手兼容文本表达真实项目/语义筛选。授权范围“全部知识”不能代替本轮统计口径。

### 5. 持久化、失败与兼容

复用 `context_meta_json` 保存版本化命名空间：协议/提示词版本、固定输入任务版本与消息句柄、任务选择、条件增量、候选状态、提交状态。实际查询计划仍以 `structured_query_plan_json` 为执行来源，任务版本仅引用该计划；完整数字和列表继续存于结果快照，不复制为任务事实。恢复已固化计划时沿用其语义，执行前照常核验当前项目和对象权限。

`history_message_ids_json` 继续审计理解阶段实际看到的消息；回答可用的任务消息句柄独立保存并经服务端校验，`basis.py` 不能把前者直接当后者。任务版本和结果在现有 Conversation 活动 Run/幂等约束内提交，不增加另一个独立推进的全局状态源。

状态分三类，避免失败结果污染继承：

1. 执行前固化候选状态与计划，供同一 Run 恢复；其他 Run 不把候选当成成功任务。
2. 正常终态且有可用结果时，与结果原子提交有效任务版本；正常空集合和正常列表截断也可提交。部分执行只有与实际可用输出对应的查询/对象状态可提交，失败输出保留未完成标记。
3. 澄清只保存未决任务，不替换有效查询版本；失败、取消只保留尝试和错误。下一轮纠正可读取最近未决/失败请求，但不能继承其未经验证的结果或新增条件。

旧 Run 不回填。首次接入从同 epoch 内可核验的旧消息、计划和结果构建标为 `legacy` 的基线；旧状态缺少条件来源时不得伪标为用户显式条件，恢复遇实质歧义时澄清。活动 epoch 内已有新协议时，按其任务版本读取，不再因旧式自动 `new_topic` 一刀切丢失恢复线索。已开始的旧协议 Run 沿原协议完成，新 Run 按持久化协议版本选择路径；遇损坏或未知新版本显式失败，不静默使用旧解析器重猜。

新路径的模型/schema/状态校验失败必须记录 fallback；不能把有条件统计回退为无条件统计或有限语义结果再宣称完成。可以准确保持已固化条件和操作时才执行兼容路径，否则返回可见失败/具体澄清。旧协议恢复保留旧回退行为。功能开关在 Run 创建时固定，新协议进行中的 Run 不因开关关闭而切换语义；回滚应先让其结束或显式终止，不能让不识别协议的旧 Worker 接管。

### 6. 代码落点与验证入口

| 落点 | 必要调整 |
|---|---|
| `dialogue_context.py`、新增小型任务状态模块 | 装配有界任务、原始消息和未决请求；校验/归并状态、固定来源和硬边界 |
| `agents/knowledge_context.py`、`follow_up.py` | 增加任务关系和候选名称协议，保留外部上下文模式与真实对象句柄 |
| `runner.py`、结果路由、`structured_entry_search.py` | 传递同一份可信任务输入，原始消息不丢失；版本化保存和恢复，不增加重复解析阶段 |
| `agents/structured_query.py`、查询规范化服务 | 增量条件协议编译为现有 EntrySetSpec 与输出，复用精确项目解析和执行器 |
| `basis.py`、复合回答/兼容分支输入 | 按已选任务装配用户陈述与依据限制，隔离暂停任务；不迁移调查或复合执行图 |
| 既有结果快照、兼容摘要及原生适配测试 | 显示实际统计口径；优先复用已有字段，不新增任务管理界面 |
| 多轮评测 | 记录任务选择、条件增量、执行参数、数字、完整性、调用数、耗时与模型用量 |

验证按状态变化组织：替换与撤销、深入后恢复、插话后恢复、澄清后补全、纠正错误解释、结果对象引用、显式重置和权限隔离。使用两个非空且数目不同的项目、空项目、同名项目以及跨项目同主题记录，避免数字碰巧正确；数据库预期独立于模型产生。对等价改写检查执行计划等价，对类型切换检查旧类型不残留，对相同精确集合检查分组和等于总数；仅在无截断、无语义召回且相同数据快照等前提成立时断言这些性质。

真实 demo 对照在相同数据快照、模型与设置下重复运行；若用户继续修改数据，记录变化并重新建立预期，不沿用旧数量。保留未用于调提示词的表达与任务组合，按完整对话划分调试集和保留集，避免共享相同轨迹的改写泄漏。人工标定真正歧义，单独统计恰当澄清、错误继承、多余澄清及纠正后恢复率；用户本次五轮原话保留为回归证据，不能靠将所有困难追问标为歧义提高分数。

进入实现验收前固定测试集和评分规则。关键权限、依据与恢复边界必须全部通过；明确状态变化在保留集上相对旧版改善，且已有开放讨论、对象指代不回退。性能同时报告调用次数、输入输出 token（可取得时）及延迟分布，真实执行后再决定是否值得合并路由。模型理解仍可能出错，自动通过不代替原生用户验收。

## Risks / Trade-offs

- 历史边界错误可能误带筛选条件：区分任务池的意图线索与所选任务的执行/事实输入，范围变化、显式重置、消息顺序、恢复和跨用户测试必须覆盖。
- demo 数据会变化且相同计数可能掩盖错误：测试构造不同计数和交叉主题；真实评测检查实际集合范围并记录当轮数据快照。
- 模型语义不稳定：用原始、多轮和独立变体验证；修复通用输入/状态/工具规则，不增加针对场景的题型路由。
- 原生分组新增 label：增加适配器与 schema 测试，用户执行项目分组和连续追问手动验收后再归档。
- 状态增加可能放大错误记忆与延迟：保留条件来源、硬边界和字节预算；先使用有界任务版本，不引入长期记忆或无限任务图。
- 全部合并为一个规划模型会扩大复合回答和调查的改造：本轮保留分工，通过共享原始输入和结构化状态消除改写句的单点依赖；更大规模合并依据评测另行决定。

## Migration Plan

用户已确认修订设计，业务实现已按本方案接入。实施前与收尾按工程规则完成全库严格校验；实施后按相关后端测试、原生测试/typecheck/lint、真实 demo 对照验证。复用现有 Run JSON 字段，无新增数据库迁移，不回填用户历史。保存本地阶段提交，等待适用的原生验收与归档批准，不推送或合并。
