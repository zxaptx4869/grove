# 知识 Agent 开放对话与工具架构

> 本文档整理 2026-09-01 围绕 Knowledge Agent 下一阶段形态的连续讨论，重点回答：如何从当前固定检索流程演进为受限工具型 Agent，如何同时支持开放讨论、知识查询、主动沉淀建议与未来增删改。
>
> 本文档是可持续更新的讨论稿，不是产品蓝图或实现规格，不代表其中能力已经完成。落地时仍需根据真实场景拆分 OpenSpec change，并在对应 proposal、specs、design 与 tasks 中锁定边界。

## 0. 核心结论

Grove 的目标不应只是一个“基于已有 Entry 回答问题”的知识库阅读器，而应逐步成为一个 **Knowledge Conversation Agent（知识对话 Agent）**：

- 用户可以在没有明确任务的情况下与 AI 讨论、答疑和共同思考；
- AI 可以按问题需要结合 Grove 已有知识、用户当前陈述和模型通用能力；
- 查询任务中，Agent 可以在应用控制边界内自主选择和组合只读工具；
- 讨论形成稳定、可复用的结论后，AI 可以提出非阻塞的新增、补充或修订建议；
- 用户接受建议后，Agent 只负责准备 Draft，正式写入仍由应用服务在用户明确确认后执行；
- 回答和沉淀结果必须区分信息依据、内容性质、形成来源与核验状态。

目标不是完全开放、可以任意访问数据库和执行写操作的 Agent，而是：

> Agent 自主理解、规划、讨论和准备；应用服务控制权限、预算、事实依据、确认与副作用。

## 1. 为什么需要调整当前架构

截至 2026-09-01，Knowledge Agent 已完成持续对话、上下文工作集、快速回答、有界调查、引用核验、结构化 Entry 查找、Candidate Draft 和单 Entry 修订等纵向能力。

但当前执行方式整体仍是“带局部 Agent 决策的受控 Workflow”：

```text
快速回答
  → 搜索正式知识
  → 读取 Entry
  → 读取 Evidence
  → 生成回答

结构化找知识
  → 混合召回
  → 重排
  → 装配 Entry 快照
  → 返回列表

深度调查
  → 模型决定下一轮搜索文本或停止
  → 应用固定执行搜索、读取 Entry、读取 Evidence
  → 继续下一轮或综合回答
```

模型已经能决定上下文关系、结果形态、回答深度、下一轮查什么以及何时停止，但不能根据问题自由选择“语义检索、结构化筛选、精确统计或 Evidence 读取”等不同求解方法。

“房子装修项目一共有多少条知识”的实测暴露了这个缺口：

- 结构化搜索只能返回受限相关结果快照，不能把快照数量当成项目总数；
- 快速回答只读取有限 Entry，却可能由模型错误推断精确总数；
- 为“计数、排序、最近更新、按类型分组”等题型逐条增加路由，只会形成不断膨胀且互相重叠的分类规则。

因此下一步不应继续扩张细粒度路由，而应让 Agent 在稳定的只读工具原语中选择求解方法。

## 2. 自主程度：选择受限工具型 Agent

三种架构的主要差异如下：

| 方案 | 工具顺序 | 新表达与能力组合 | 可预测性 | 适合 Grove |
|---|---|---|---|---|
| 固定 Workflow | 代码写死 | 经常补路由和流程 | 高 | 已出现扩展瓶颈 |
| 受限工具型 Agent | 模型在白名单内选择和组合 | 多数可由现有工具泛化 | 中高 | 推荐方向 |
| 完全开放式 Agent | 模型自由规划较长步骤 | 最灵活 | 较低 | 当前不适合 |

受限工具型 Agent 解决的是：

- 同一种需求的不同表达不再需要新规则；
- 现有能力的新组合通常不再需要新流程；
- 快速与深度模式可以复用同一套工具，只使用不同预算；
- 新增一个查询维度后，列表、统计和组合问题可以共同使用。

它不能消除真正的新产品开发：新的业务判断、新数据来源和新的副作用仍需增加工具、服务与交互。例如“哪些知识已经过时”需要定义过时标准，“删除这些知识”需要回收站、影响分析和强确认。健康的目标不是以后永远不改，而是只在真正新增能力时改，不再因为用户换一种说法就改。

## 3. 总体架构

```text
用户消息
   ↓
服务端固定校验
登录 / Workspace / 项目 / 幂等 / 并发
   ↓
上下文理解
继续话题 / 新话题 / 澄清 / 独立问题改写
   ↓
对话与任务规划
正常讨论 / 综合回答 / Entry 列表 / 准备知识操作
快速预算 / 深度预算
信息依据策略
   ↓
Knowledge Conversation Agent
   ├─ 不调用工具，使用模型通用能力讨论
   ├─ 自主调用受限只读工具
   ├─ 观察工具结果后继续或停止
   ├─ 生成回答、列表或澄清
   └─ 可附带非阻塞的知识操作建议
   ↓
用户接受操作建议或显式发起操作
   ↓
Operation Draft
目标 / 内容 / 差异 / 依据 / 影响 / 风险
   ↓
用户明确确认
   ↓
应用服务执行
权限 / 版本 / 事务 / 幂等 / 回执 / 撤销
```

这里包含两个不同的自主性边界：

1. **只读求解自主性**：Agent 可以在白名单内自主选择工具、组合步骤和停止时机。
2. **知识变更自主性**：Agent 可以识别机会和准备方案，但不能自行确认或执行正式写入。

## 4. 路由只保留产品级大分叉

“路由”指收到消息后判断进入哪一种预设的大型处理契约，不是 HTTP 或页面路由。路由本身通常也是一次返回结构化结果的模型调用。

### 4.1 建议保留的判断

第一类是上下文边界：

```text
continue   继续当前话题
new_topic  开始新话题
clarify    当前信息不足，需要澄清
```

它决定是否继承工作集、怎样消解指代、是否创建新主题，以及是否应暂停执行等待用户补充。

第二类是结果契约与预算：

```text
result_form:
  respond             正常讨论或综合回答
  entries             Entry 对象列表
  prepare_operation   准备知识操作

effort:
  quick               一次规划、少量调用
  investigate         有界多轮调查
```

`result_form` 和 `effort` 可以由同一次结构化规划返回，不必继续拆成多个小路由器。用户通过界面或自然语言给出明确覆盖时，应用直接尊重用户选择，不再让模型重新猜测。

### 4.2 不应成为路由的细粒度问题

以下问题应交给工具规划，而不是继续增加大分叉：

- 是不是计数问题；
- 是否按项目、目录或类型分组；
- 是否查询最近更新；
- 是否寻找最大、最小或某个时间段；
- 应使用语义搜索、结构化筛选还是精确统计；
- 是否需要继续读取 Entry 或 Evidence；
- 多个只读查询工具如何组合。

路由负责“用户最终想看到什么、允许花多少成本”，Agent 负责“具体怎样取得可靠事实”。

## 5. 查询能力：稳定原语而不是题型工具

### 5.1 推荐的只读工具原语

#### `semantic_search_entries`

处理内容语义相关性：

- “装修时哪里需要预留插座？”
- “帮我找鞋柜防臭的知识。”

#### `query_entries`

处理确定性筛选、排序和分页：

- “列出最近修改的 5 条装修知识。”
- “找出经验类型的知识。”
- “施工阶段目录有哪些知识？”

#### `aggregate_entries`

处理计数、分组、排名和时间分布：

- “房子装修项目共有多少条知识？”
- “每个项目分别有多少条？”
- “按知识类型统计。”
- “哪个项目的知识最多？”

#### `read_entries` / `read_entry_evidence`

处理对象详情、内容理解、比较、引用与冲突核验。

### 5.2 统一的知识集合描述

为避免每个工具各自发明筛选语义，可逐步形成受限的 `EntrySetSpec`：

```text
EntrySetSpec
├─ scope                 Workspace / 当前项目 / 已校验项目
├─ semantic_query        可选语义条件
├─ filters
│  ├─ 项目
│  ├─ 目录
│  ├─ 知识类型
│  ├─ 创建/更新时间
│  └─ 来源数量等允许字段
├─ sort                  创建时间 / 更新时间 / 数量
├─ aggregate             count / group count / min / max
└─ limit                 服务端固定上限
```

模型不能编写 SQL、指定任意 Workspace、绕过项目权限或放大预算。模型只生成结构化意图，应用服务负责对象解析、字段白名单、范围校验、执行与结果审计。

### 5.3 快速与深度复用同一套工具

```text
quick
  → 最多一次规划和少量工具调用

investigate
  → 最多若干轮规划
  → 每轮观察结果后决定补查、回答或不足
```

“快速/深度”是预算配置，不应再对应两套长期分叉的查询实现。

## 6. 开放讨论是默认能力，不要求已有知识

Knowledge Agent 的默认状态不是等待用户下达明确任务。用户可以因为不了解某件事而开始讨论，目标在过程中逐渐形成。

```text
用户提出问题或困惑
  → AI 解释、追问、检索或提出不同视角
  → 用户补充个人情况
  → 双方形成观点、经验或决定
  → AI 发现值得沉淀的机会
  → 提出轻量建议
  → 用户接受后才生成 Draft
```

讨论不应强制依赖 Grove 已有 Entry。否则 AI 会退化为知识库复述器，无法帮助用户从“不知道”走到“理解”。Agent 可以：

- 完全不调用工具，使用模型通用能力解释或启发；
- 读取 Grove，联系用户已有经验和历史决定；
- 结合用户当前陈述进行个性化分析；
- 未来在需要时调用外部搜索或专业数据工具进行实时核验。

讨论可以比正式知识更开放，允许假设、比较与探索；一旦进入沉淀流程，就必须提高来源、性质、核验与确认要求。

## 7. 信息依据策略

### 7.1 不采用单一固定优先级

默认不应“永远先查 Grove”或“永远先用模型”。依据选择顺序是：

1. 用户明确约束最高；
2. 根据问题性质选择主要依据；
3. 根据事实风险与时效要求收紧来源；
4. 相关 Grove 知识用于个性化和历史联系；
5. 模型通用能力用于解释、推理和启发。

内部可以使用少量稳定策略：

```text
knowledge_only      只根据 Grove
knowledge_first     先使用用户知识，再由模型补充
model_first         通用解释为主，相关时联系用户知识
hybrid              Grove、用户陈述和模型能力共同分析
external_required   必须有实时或权威外部来源
```

这些是信息依据策略，不是为每个自然语言题型添加的路由。

### 7.2 不同来源的权威范围不同

| 来源 | 最适合回答 | 不能冒充 |
|---|---|---|
| 当前用户陈述 | 最新个人意图、经验和决定 | 普遍客观事实 |
| Grove 正式知识 | 用户历史记录、项目状态、已有来源 | 当前外部世界的最新事实 |
| 模型通用知识 | 解释、推理、建议和启发 | 已联网核验或用户已有记录 |
| 可信外部来源（未来） | 法规、标准、价格、产品和时效事实 | 用户个人意图 |

如果当前用户陈述与旧 Grove Entry 冲突，应指出变化并建议修订，不静默覆盖；如果外部资料与 Grove 旧记录冲突，应并列展示并保留双方依据；模型通用知识不能在没有证据时裁决为客观事实。

### 7.3 回答中的依据表达

界面不必为每句话增加冗长免责声明，但应提供简洁、可展开的依据说明：

```text
依据：你的知识 2 条 · AI 通用知识补充

AI 通用知识 · 未使用你的知识库 · 未进行外部核验

你的知识 2 条 · 外部来源 3 条 · 已核验
```

Citation 只能指向真实 Grove Evidence 或未来真实外部来源；模型通用知识不得制造假引用。混合回答发生来源冲突时，应在相关结论附近明确区分，不用统一的“来源优先级”偷偷裁决。

## 8. 讨论中主动建议知识沉淀

### 8.1 建议和草稿必须分开

一次正常回复可以附带可选建议，但建议本身不创建 Draft：

```text
AssistantTurn
├─ reply
├─ citations / basis summary
└─ suggested_operations
   ├─ create_knowledge
   ├─ supplement_entry
   └─ revise_entry
```

只有用户点击建议或明确说“帮我保存、总结、补充、修改”后，才提交结构化 `prepare_operation` 请求并创建 Operation Run。

### 8.2 适合提出建议的条件

建议至少需要多个信号共同成立：

- 当前话题形成了相对稳定且可复用的结论；
- 用户表达了接受、选择、决定或亲身经验，而不只是礼貌回应；
- 与已有知识相比确实存在新增、补充或修订价值；
- 没有影响结论的重大未解决分歧；
- 当前话题近期没有提示过或被用户拒绝过。

AI 不应把每一句“好的”“有道理”都识别为保存意图。建议应使用回复后的轻量按钮或小卡，不弹出阻塞界面；每个稳定话题限制建议频率，被忽略或拒绝后进入冷却。接受、忽略和拒绝可以成为后续优化主动建议阈值的行为信号。

### 8.3 有目标与无目标讨论

针对某条 Entry 的讨论可以携带目标句柄，帮助 Agent 解释和提出补充或修订建议，但该句柄不构成写入授权；生成 Draft 前必须重新校验当前版本。

没有特定对象的开放讨论中，Agent 可以先检查是否存在相关 Entry：

- 没有相关 Entry：建议新增；
- 已有内容但缺少新条件：建议补充；
- 新结论与现有 Entry 冲突：建议修订或保留冲突；
- 内容仍不确定：不建议正式沉淀，或建议保留为待验证观点。

项目范围可以默认当前项目；Workspace 范围在准备写入前必须明确目标项目。

### 8.4 保存的是当前讨论片段，不是整段历史

长 Conversation 可能包含多个主题。准备沉淀时应锚定：

- 当前主题或上下文版本；
- 选定的用户消息和 AI 回复范围；
- 本段讨论使用的 Entry 与 Evidence；
- 用户明确表达的决定；
- AI 提供但尚未核验的补充。

用户应能看到本次 Draft 使用了哪一段讨论，并可在确认前编辑最终内容。

## 9. 查询、讨论与知识操作的统一模型

```text
Knowledge Conversation Agent
├─ 开放讨论
│  ├─ 模型通用解释
│  ├─ 用户情况追问
│  ├─ 可选 Grove 查询
│  └─ 可选沉淀建议
│
├─ 只读查询
│  ├─ 语义搜索
│  ├─ 结构化筛选
│  ├─ 聚合统计
│  └─ Entry / Evidence 读取
│
├─ 操作准备
│  ├─ 新增 Candidate Draft
│  ├─ Entry Revision Draft
│  ├─ 移动方案
│  ├─ 合并方案
│  └─ 删除方案
│
└─ 受控执行
   ├─ 用户确认
   ├─ 权限与版本校验
   ├─ 事务写入
   ├─ 审计回执
   └─ 撤销或恢复
```

顶层只需要识别正常回应、展示对象、澄清和准备操作等少数任务契约。新增、补充、修订、移动、合并和删除是 `prepare_operation` 下的合法操作种类，不应各自演变成一整套自然语言路由。

## 10. 工具副作用与授权等级

| 等级 | 能力 | Agent 权限 | 示例 |
|---|---|---|---|
| L0 | 只读查询 | 可自主执行 | 搜索、筛选、统计、读取 Evidence |
| L1 | 准备草稿 | 可自主生成建议；用户发起后准备 Draft | Candidate Draft、Revision Draft、移动方案 |
| L2 | 可撤销写入 | 用户确认后由应用执行 | 修改 Entry、移动 Entry、创建 Candidate |
| L3 | 高风险或批量写入 | 强确认、影响预览、严格数量限制 | 批量合并、批量移动、删除 |
| L4 | 不可恢复或外部副作用 | 默认不开放或单独授权 | 永久删除、外部发布 |

最终提交函数不必作为模型可调用工具暴露。更安全的方式是：

```text
模型可以：prepare_entry_revision(...)

模型不能：commit_entry_revision(...)

用户确认后：应用服务调用 commit_entry_revision(...)
```

这样模型即使错误规划，也不能绕过用户确认。

## 11. 通用 Operation Plan

为避免未来每增加一种操作就重建会话、确认、恢复与审计，可以逐步抽象统一操作协议：

```text
OperationPlan
├─ operation_kind          create / revise / move / merge / delete
├─ targets                 操作对象
├─ expected_versions       草稿生成时的对象版本
├─ proposed_changes        建议变更
├─ evidence                使用的依据
├─ destination             目标项目或目录，可选
├─ impact                  影响范围
├─ risk_level              风险等级
├─ undo_capability         是否可撤销
└─ confirmation_token      绑定本次确认
```

统一状态可以是：

```text
preparing
→ ready_for_review
→ confirmed
→ executing
→ completed / failed
→ undone
```

每种操作仍需要自己的领域校验和服务处理器，但可以共用对象选择、版本保护、Draft、确认、幂等、回执、历史恢复和撤销框架。

## 12. 内容性质、形成来源与核验状态

开放讨论允许模型通用知识、用户陈述与 Grove Evidence 混合。如果把所有内容都压进现有 `main_type` 或 `info_nature`，会混淆“这是什么内容”和“它从哪里形成”。建议后续至少按两个独立维度讨论数据模型。

### 12.1 内容性质

```text
事实
经验
个人决策
建议
待验证观点或假设
```

### 12.2 形成来源

```text
Grove Evidence
用户陈述
AI 通用知识
外部核验来源
多种来源混合形成
```

还可以独立表达核验状态：有来源支持、用户确认但未外部核验、待验证、混合依据等。

同一条内容可能是：

```text
内容性质：个人决策
形成来源：用户陈述 + AI 通用建议
```

也可能是：

```text
内容性质：事实
形成来源：Grove Evidence + 外部核验来源
```

“对话可追溯”只证明 AI 和用户当时说过什么，不证明 AI 的通用知识客观正确。对话 Source 应记录选定消息、模型 provider/model、所用 Evidence、用户编辑和最终确认，但不能把 AI 生成内容伪装成已核验来源。

## 13. 诚实性与事实约束

以下约束不应只依赖提示词：

- 精确总数、占比、排名等数字必须来自服务端可验证的统计结果；
- 搜索命中数、快照条数和 Evidence 数量不得被描述为范围总数；
- Citation 必须指向当前 Run 核验过的真实 Evidence 或未来真实外部来源；
- AI 通用知识必须可识别，不得伪装成 Grove 记录或已联网核验；
- 结构化工具结果应保存范围、参数、时间和结果句柄，供回答校验与审计；
- 来源冲突必须并列呈现，不由模型静默覆盖用户知识；
- 没有必要依据时可以继续开放讨论，但进入正式沉淀前必须说明内容性质和形成来源。

## 14. 渐进演进建议

这份架构是长期方向，不代表一次 change 全部实现。合理顺序可能是：

1. 建立查询场景地图和小型评估集，覆盖内容问答、对象查找、筛选、统计、混合问题与失败路径；
2. 抽取统一只读工具执行器和结构化工具结果账本；
3. 增加 `query_entries`、`aggregate_entries` 与受限 `EntrySetSpec`；
4. 让快速回答先使用“一次规划 → 工具执行 → 回答”；
5. 让深度调查复用同一工具集，在更高预算下多轮规划；
6. 放开默认讨论使用模型通用能力，并增加回答依据说明；
7. 支持用户显式“总结本段讨论”，建立对话片段 Draft 与来源表达；
8. 在有真实接受/拒绝数据后增加非阻塞的主动沉淀建议；
9. 抽象通用 Operation Plan，再逐步接入移动、合并、删除和批量操作；
10. 未来再评估外部搜索、实时核验与主动 Discovery。

每一阶段都应使用代表性场景评估，而不是为单条问法添加路由规则。

## 15. 仍需继续讨论的问题

1. `respond / entries / prepare_operation` 是否由同一次规划调用决定，还是保留独立结果形态路由？
2. 快速模式允许几次工具调用，怎样在低延迟下支持“统计后再列出对象”等组合？
3. `EntrySetSpec` 第一阶段开放哪些筛选、分组和排序字段？
4. 回答依据应在整条回答、结构化要点还是单个结论级表达？
5. AI 通用知识形成的 Candidate 应使用哪些内容性质、来源和核验状态？
6. 用户个人决定是否可以直接作为正式 Entry 的有效来源，还是仍须经过 Candidate 确认台？
7. 主动沉淀建议的触发阈值、冷却和行为信号怎样设计？
8. 对话片段边界由当前主题版本自动确定，还是允许用户选择消息范围？
9. 哪些写操作可以复用通用 Operation Plan，哪些因风险必须保持专用状态机？
10. Web 与原生 App 如何共享同一领域协议，同时保持各自合适的交互形态？
