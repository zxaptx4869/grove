# 知识 Agent 开放对话与工具架构

> 本文档整理 2026-09-01 至 2026-09-02 围绕 Knowledge Agent 下一阶段形态的连续讨论，重点回答：如何从当前固定检索流程演进为受限工具型 Agent，如何同时支持开放讨论、知识查询、主动沉淀建议与未来增删改。
>
> 本文档是可持续更新的讨论稿，不是产品蓝图或实现规格，不代表其中能力已经完成。落地时仍需根据真实场景拆分 OpenSpec change，并在对应 proposal、specs、design 与 tasks 中锁定边界。

## 0. 核心结论

Grove 的目标不应只是一个“基于已有 Entry 回答问题”的知识库阅读器，而应逐步成为一个 **Knowledge Conversation Agent（知识对话 Agent）**：

- 用户可以在没有明确任务的情况下与 AI 讨论、答疑和共同思考；
- AI 可以按问题需要结合 Grove 已有知识、用户当前陈述和模型通用能力；
- 查询任务中，Agent 可以在应用控制边界内自主选择和组合只读工具；
- 讨论形成稳定、可复用的结论后，AI 可以提出非阻塞的新增、补充或修订建议；
- 用户接受建议后，Agent 只负责准备 Operation Plan；正式写入仍由应用服务在用户明确审阅确认后执行；
- 对话中的完整 Operation Review 可以作为一次有效人工确认，确认后直接形成正式 Entry；用户选择稍后处理时才进入 pending Candidate；
- 回答和沉淀结果必须区分内容性质与形成来源，但 Grove 不替用户给知识设置统一真实性或可靠性等级；
- 固定挂在回答卡上的“整理成知识”属于早期过渡能力，长期由自然语言请求、上下文建议和通用知识操作协议替代。

目标不是完全开放、可以任意访问数据库和执行写操作的 Agent，而是：

> Agent 自主理解、规划、讨论和准备；应用服务控制权限、预算、可追溯依据、确认与副作用。

## 1. 为什么需要调整当前架构

截至 2026-09-01，Knowledge Agent 已完成持续对话、上下文工作集、快速回答、有界调查、引用核验、结构化 Entry 查找、Candidate Draft 和单 Entry 修订等纵向能力。

但当前执行方式整体仍是“带局部 Agent 决策的受控 Workflow”：

```text
快速回答
  → 搜索正式知识
  → 读取 Entry
  → 读取 Evidence
  → 生成回答

结构化找知识
  → 混合召回
  → 重排
  → 装配 Entry 快照
  → 返回列表

深度调查
  → 模型决定下一轮搜索文本或停止
  → 应用固定执行搜索、读取 Entry、读取 Evidence
  → 继续下一轮或综合回答
```

模型已经能决定上下文关系、结果形态、回答深度、下一轮查什么以及何时停止，但不能根据问题自由选择“语义检索、结构化筛选、精确统计或 Evidence 读取”等不同求解方法。

“房子装修项目一共有多少条知识”的实测暴露了这个缺口：

- 结构化搜索只能返回受限相关结果快照，不能把快照数量当成项目总数；
- 快速回答只读取有限 Entry，却可能由模型错误推断精确总数；
- 为“计数、排序、最近更新、按类型分组”等题型逐条增加路由，只会形成不断膨胀且互相重叠的分类规则。

因此下一步不应继续扩张细粒度路由，而应让 Agent 在稳定的只读工具原语中选择求解方法。

## 2. 自主程度：选择受限工具型 Agent

三种架构的主要差异如下：

| 方案 | 工具顺序 | 新表达与能力组合 | 可预测性 | 适合 Grove |
|---|---|---|---|---|
| 固定 Workflow | 代码写死 | 经常补路由和流程 | 高 | 已出现扩展瓶颈 |
| 受限工具型 Agent | 模型在白名单内选择和组合 | 多数可由现有工具泛化 | 中高 | 推荐方向 |
| 完全开放式 Agent | 模型自由规划较长步骤 | 最灵活 | 较低 | 当前不适合 |

受限工具型 Agent 解决的是：

- 同一种需求的不同表达不再需要新规则；
- 现有能力的新组合通常不再需要新流程；
- 快速与深度模式可以复用同一套工具，只使用不同预算；
- 新增一个查询维度后，列表、统计和组合问题可以共同使用。

它不能消除真正的新产品开发：新的业务判断、新数据来源和新的副作用仍需增加工具、服务与交互。例如“哪些知识已经过时”需要定义过时标准，“删除这些知识”需要回收站、影响分析和强确认。健康的目标不是以后永远不改，而是只在真正新增能力时改，不再因为用户换一种说法就改。

## 3. 总体架构

```text
用户消息
   ↓
服务端固定校验
登录 / Workspace / 项目 / 幂等 / 并发
   ↓
上下文理解
继续话题 / 新话题 / 澄清 / 独立问题改写
   ↓
对话与任务规划
正常讨论 / 综合回答 / Entry 列表 / 准备知识操作
快速预算 / 深度预算
信息依据策略
   ↓
Knowledge Conversation Agent
   ├─ 不调用工具，使用模型通用能力讨论
   ├─ 自主调用受限只读工具
   ├─ 观察工具结果后继续或停止
   ├─ 生成回答、列表或澄清
   └─ 可附带非阻塞的知识操作建议
   ↓
用户接受操作建议或显式发起操作
   ↓
准备操作
固定整理对象 / 检索相似知识 / 判断内容关系
   ↓
Operation Plan / Review
目标 / 内容 / 差异 / 形成来源 / 影响 / 风险
   ↓
用户明确确认
   ↓
应用服务执行
权限 / 版本 / 事务 / 幂等 / 回执 / 撤销
```

这里包含两个不同的自主性边界：

1. **只读求解自主性**：Agent 可以在白名单内自主选择工具、组合步骤和停止时机。
2. **知识变更自主性**：Agent 可以识别机会和准备方案，但不能自行确认或执行正式写入。

## 4. 路由只保留产品级大分叉

“路由”指收到消息后判断进入哪一种预设的大型处理契约，不是 HTTP 或页面路由。路由本身通常也是一次返回结构化结果的模型调用。

### 4.1 建议保留的判断

第一类是上下文边界：

```text
continue   继续当前话题
new_topic  开始新话题
clarify    当前信息不足，需要澄清
```

它决定是否继承工作集、怎样消解指代、是否创建新主题，以及是否应暂停执行等待用户补充。

第二类是结果契约与预算：

```text
result_form:
  respond             正常讨论或综合回答
  entries             Entry 对象列表
  prepare_operation   准备知识操作

effort:
  quick               一次规划、少量调用
  investigate         有界多轮调查
```

`result_form` 和 `effort` 可以由同一次结构化规划返回，不必继续拆成多个小路由器。用户通过界面或自然语言给出明确覆盖时，应用直接尊重用户选择，不再让模型重新猜测。

### 4.2 不应成为路由的细粒度问题

以下问题应交给工具规划，而不是继续增加大分叉：

- 是不是计数问题；
- 是否按项目、目录或类型分组；
- 是否查询最近更新；
- 是否寻找最大、最小或某个时间段；
- 应使用语义搜索、结构化筛选还是精确统计；
- 是否需要继续读取 Entry 或 Evidence；
- 多个只读查询工具如何组合。

路由负责“用户最终想看到什么、允许花多少成本”，Agent 负责“具体怎样取得所需信息”。

## 5. 查询能力：稳定原语而不是题型工具

### 5.1 推荐的只读工具原语

#### `semantic_search_entries`

处理内容语义相关性：

- “装修时哪里需要预留插座？”
- “帮我找鞋柜防臭的知识。”

#### `query_entries`

处理确定性筛选、排序和分页：

- “列出最近修改的 5 条装修知识。”
- “找出经验类型的知识。”
- “施工阶段目录有哪些知识？”

#### `aggregate_entries`

处理计数、分组、排名和时间分布：

- “房子装修项目共有多少条知识？”
- “每个项目分别有多少条？”
- “按知识类型统计。”
- “哪个项目的知识最多？”

#### `read_entries` / `read_entry_evidence`

处理对象详情、内容理解、比较、引用与冲突核验。

### 5.2 统一的知识集合描述

为避免每个工具各自发明筛选语义，可逐步形成受限的 `EntrySetSpec`：

```text
EntrySetSpec
├─ scope                 Workspace / 当前项目 / 已校验项目
├─ semantic_query        可选语义条件
├─ filters
│  ├─ 项目
│  ├─ 目录
│  ├─ 知识类型
│  ├─ 创建/更新时间
│  └─ 来源数量等允许字段
├─ sort                  创建时间 / 更新时间 / 数量
├─ aggregate             count / group count / min / max
└─ limit                 服务端固定上限
```

模型不能编写 SQL、指定任意 Workspace、绕过项目权限或放大预算。模型只生成结构化意图，应用服务负责对象解析、字段白名单、范围校验、执行与结果审计。

### 5.3 快速与深度复用同一套工具

```text
quick
  → 最多一次规划和少量工具调用

investigate
  → 最多若干轮规划
  → 每轮观察结果后决定补查、回答或不足
```

“快速/深度”是预算配置，不应再对应两套长期分叉的查询实现。

## 6. 开放讨论是默认能力，不要求已有知识

Knowledge Agent 的默认状态不是等待用户下达明确任务。用户可以因为不了解某件事而开始讨论，目标在过程中逐渐形成。

```text
用户提出问题或困惑
  → AI 解释、追问、检索或提出不同视角
  → 用户补充个人情况
  → 双方形成观点、经验或决定
  → AI 发现值得沉淀的机会
  → 提出轻量建议
  → 用户接受后才进入操作准备
```

讨论不应强制依赖 Grove 已有 Entry。否则 AI 会退化为知识库复述器，无法帮助用户从“不知道”走到“理解”。Agent 可以：

- 完全不调用工具，使用模型通用能力解释或启发；
- 读取 Grove，联系用户已有经验和历史决定；
- 结合用户当前陈述进行个性化分析；
- 未来在需要时调用外部搜索或专业数据工具获取当前材料。

讨论可以比正式知识更开放，允许假设、比较与探索；一旦进入沉淀流程，就必须明确内容性质、形成来源和最终确认对象，但不需要把个人知识库改造成事实核验系统。

## 7. 信息依据策略

### 7.1 不采用单一固定优先级

默认不应“永远先查 Grove”或“永远先用模型”。不同来源各自适合回答不同问题，不构成统一的可信等级。依据选择顺序是：

1. 先尊重用户明确约束，例如只使用个人知识或不要联网；
2. 根据问题性质选择主要依据；
3. 涉及当前时效、专业规则或较高风险时，明确现有能力边界，未来再按需使用外部工具；
4. 相关 Grove 知识用于个性化、历史决定和项目联系；
5. 模型通用能力用于解释、推理和启发。

内部可以使用少量稳定策略：

```text
knowledge_only      只根据 Grove
knowledge_first     先使用用户知识，再由模型补充
model_first         通用解释为主，相关时联系用户知识
hybrid              Grove、用户陈述和模型能力共同分析
external_needed     需要当前外部材料，现阶段可能无法完成
```

这些是信息依据策略，不是为每个自然语言题型添加的路由。

### 7.2 不同来源的适用范围不同

| 来源 | 最适合回答 | 不能冒充 |
|---|---|---|
| 当前用户陈述 | 最新个人意图、经验和决定 | 所有人的普遍结论 |
| Grove 正式知识 | 用户选择保留的历史记录、项目状态和已有材料 | 当前外部世界的最新状态 |
| 模型通用知识 | 解释、推理、建议和启发 | 用户已有记录或真实外部 Source |
| 外部材料（未来） | 提供可查看的当前材料、不同观点和专业信息 | 自动可靠或已经由 Grove 判真 |

有 Source 只能证明内容来自哪里，不表示材料一定可靠；一张其他 AI 回答截图同样可以是真实 Source，但不能因此标成“已核验事实”。如果当前用户陈述与旧 Grove Entry 不一致，应指出变化并建议修订，不静默覆盖；不同材料互相冲突时应并列展示，由用户判断是否修订、分别保留或继续查找。

### 7.3 回答中的依据表达

界面不必为每句话增加冗长免责声明，但应提供简洁、可展开的依据说明：

```text
依据：你的知识 2 条 · AI 通用知识补充

AI 通用知识 · 未使用你的知识库 · 未检索实时外部资料

你的知识 2 条 · 参考外部材料 3 条
```

Citation 只能指向真实 Grove Evidence 或未来真实外部材料；模型通用知识不得制造假引用。默认在整条回答下提供紧凑、可展开的依据概览，不为每句话增加标签；只有来源切换、内容冲突或必须说明时效边界时，才在相关结论附近单独区分。

## 8. 讨论中主动建议知识沉淀

### 8.1 建议和草稿必须分开

一次正常回复可以附带可选建议，但建议本身不创建 Draft：

```text
AssistantTurn
├─ reply
├─ citations / basis summary
└─ suggested_operations
   ├─ create_knowledge
   ├─ supplement_entry
   └─ revise_entry
```

只有用户点击建议或明确说“帮我保存、总结、补充、修改”后，才提交结构化 `prepare_operation` 请求并创建 Operation Run。建议本身不创建 Draft，也不向待处理区塞入用户没有同意的 Candidate。

### 8.2 适合提出建议的条件

建议至少需要多个信号共同成立：

- 当前话题形成了相对稳定且可复用的结论；
- 用户表达了接受、选择、决定或亲身经验，而不只是礼貌回应；
- 没有影响结论的重大未解决分歧；
- 内容具有未来再次查找、修改或引用的价值。

AI 不应把每一句“好的”“有道理”“我再想想”识别为保存意图。建议应使用回复后的轻量按钮或小卡，不弹出阻塞界面，也不设置“同一话题只能提示一次”的僵硬规则；只需避免连续重复同一建议。第一阶段不增加关闭主动建议的设置，先记录建议展示、点击、忽略或拒绝、Draft 生成和最终确认结果，供以后人工评估阈值，不让 Agent 自行调参。

### 8.3 有目标与无目标讨论

针对某条 Entry 的讨论可以携带目标句柄，帮助 Agent 解释和提出补充或修订建议，但该句柄不构成写入授权；生成 Draft 前必须重新校验当前版本。

没有特定对象的开放讨论中，建议先表达“要整理什么”，而不是在每轮回答前为了判断新增或补充而检索整个知识库：

- `整理这个决定`：只整理最终决定及其必要背景；
- `保存这段经验`：整理用户描述的亲身经历和结论；
- `整理成方法`：提炼具有复用价值的操作方法；
- `总结本段讨论`：范围更宽，可以形成一个或多个结论。

用户接受后，`prepare_operation` 再检索可能相关的 Entry，判断独立、相同、补充或差异关系，并生成与最终动作匹配的 Draft。当前上下文已经明确目标 Entry 时，才可以直接显示 `补充《标题》` 或 `修订《标题》`；目标随后失效或版本变化时应停止并解释，不能静默改成新增。

项目范围可以默认当前项目；Workspace 范围在准备写入前必须明确目标项目。

### 8.4 整理的是当前讨论片段，不是整段历史

长 Conversation 可能包含多个主题。准备沉淀时应锚定：

- 当前主题或上下文版本；
- 选定的用户消息和 AI 回复范围；
- 本段讨论使用的 Entry 与 Evidence；
- 用户明确表达的决定；
- AI 通用能力提供的解释或建议。

默认由 Agent 自动选择从问题出现到结论形成的必要消息，不要求用户逐条勾选。用户应能看到“形成自本次讨论中的 N 条消息”并按需展开；范围不合适时，优先通过“只保留最后的决定”“不要前面的预算部分”等自然语言调整，再重新生成 Draft。

是否拆成多条不按消息数量判断，而按未来是否需要分别查找、修改或引用判断。具体按钮只整理它所表达的对象，例如 `整理这个决定` 默认只生成个人决定；只有 `总结本段讨论` 等宽范围动作才允许提出多条 Draft，并在确认前让用户取消、合并或分别编辑。

### 8.5 用户先同意整理，准备阶段再确定落库方式

目标未知时，用户点击 `整理这个决定` 表示同意保留这部分内容，不代表同意“新增一条 Entry”。系统随后在同一次准备阶段完成内容提取、相似知识检索、关系判断和操作 Draft 生成：

```text
同意整理
  → 固定讨论片段
  → 检索相关 Entry
  → 判断独立 / 相同 / 补充 / 差异
  → 生成新增 / 不重复创建 / 补充 / 修订 / 分别保留方案
  → 用户审阅确认
```

界面准备状态可以写“正在整理，并检查是否已有相关知识”。用户第一次看到的 Draft 就必须是动作明确的最终方案，不能先展示为新增草稿，再突然变成修订草稿。用户始终可以改为新建、选择其他目标或分别保留。

## 9. 查询、讨论与知识操作的统一模型

```text
Knowledge Conversation Agent
├─ 开放讨论
│  ├─ 模型通用解释
│  ├─ 用户情况追问
│  ├─ 可选 Grove 查询
│  └─ 可选沉淀建议
│
├─ 只读查询
│  ├─ 语义搜索
│  ├─ 结构化筛选
│  ├─ 聚合统计
│  └─ Entry / Evidence 读取
│
├─ 操作准备
│  ├─ 新增 / 补充 / 修订 Operation Plan
│  ├─ 移动方案
│  ├─ 合并方案
│  └─ 移入回收站方案
│
└─ 受控执行
   ├─ 用户确认
   ├─ 权限与版本校验
   ├─ 事务写入
   ├─ 审计回执
   └─ 撤销或恢复
```

顶层只需要识别正常回应、展示对象、澄清和准备操作等少数任务契约。新增、补充、修订、移动、合并和删除是 `prepare_operation` 下的合法操作种类，不应各自演变成一整套自然语言路由。

## 10. 工具副作用与授权等级

| 等级 | 能力 | Agent 权限 | 示例 |
|---|---|---|---|
| L0 | 只读查询 | 可自主执行 | 搜索、筛选、统计、读取 Evidence |
| L1 | 准备草稿 | 可自主生成建议；用户发起后准备 Plan | 新增、补充、修订与移动方案 |
| L2 | 可撤销写入 | 用户确认后由应用执行 | 创建或修改 Entry、移动 Entry、加入待处理 |
| L3 | 高风险或批量写入 | 强确认、影响预览、严格数量限制 | 批量合并、批量移动、移入回收站 |
| L4 | 不可恢复或外部副作用 | 默认不开放或单独授权 | 永久删除、外部发布 |

最终提交函数不必作为模型可调用工具暴露。更安全的方式是：

```text
模型可以：prepare_entry_revision(...)

模型不能：commit_entry_revision(...)

用户确认后：应用服务调用 commit_entry_revision(...)
```

这样模型即使错误规划，也不能绕过用户确认。

澄清遵循“只问会改变正式对象或影响范围的问题”：如果不确定项只影响可编辑标题、分类、措辞或推荐目录，Agent 先准备并让用户修改；如果目标项目、目标 Entry、核心内容对象或批量影响范围不明确，则先用短追问或结构化选择澄清。能够列出项目卡、Entry 卡或对象集合时，不使用宽泛开放问题。

## 11. 通用 Operation Plan

为避免未来每增加一种操作就重建会话、确认、恢复与审计，可以逐步抽象统一操作协议：

```text
OperationPlan
├─ operation_kind          create / supplement / revise / move / merge / trash
├─ targets                 操作对象
├─ expected_versions       草稿生成时的对象版本
├─ proposed_changes        建议变更
├─ formation_basis         形成来源与实际引用
├─ destination             目标项目或目录，可选
├─ impact                  影响范围
├─ risk_level              风险等级
├─ undo_capability         是否可撤销
└─ confirmation_token      绑定本次确认
```

统一状态可以是：

```text
preparing
→ ready_for_review
→ confirmed
→ executing
→ completed / failed
→ undone
```

每种操作仍需要自己的领域校验和服务处理器，但可以共用对象选择、版本保护、Draft、确认、幂等、回执、历史恢复和撤销框架。

### 11.1 统一 Operation Review，不统一操作正文

移动端对话内只显示紧凑摘要卡，完整内容、差异和影响使用 Bottom Sheet 或全屏审阅。所有 Review 共用“做什么、作用于什么、完成后怎样、如何形成、确认后后果”五类信息，但各操作的正文不同：

| 操作 | 必须展示 | 推荐确认方式 |
|---|---|---|
| 新增 | 完整内容、项目、推荐位置、形成来源 | 一次明确确认 |
| 补充 | 目标 Entry、新增部分、补充后的结果 | 一次差异确认 |
| 修订 | 原内容与新内容差异、修改理由、版本历史 | 一次差异确认 |
| 移动 | 当前归属、目标归属、影响对象 | 一次范围确认 |
| 合并 | 参与 Entry、保留主体、合并结果、原对象处理 | 全屏强确认 |
| 回收站 | 精确对象、关联影响、恢复方式 | 破坏性确认 |

能可靠撤销的操作少问一次，执行后提供撤销；不可恢复或影响多条正式知识的操作必须在确认前完整展示影响。永久删除默认不作为普通 Agent 工具开放。

### 11.2 一次完整审阅可以直接形成正式 Entry

现有“Candidate Draft → 确认创建 pending Candidate → 再到确认台确认 Entry”是早期纵向闭环，不是长期对话体验。新的 Operation Review 本身就是候选内容的人在环上确认：用户在其中检查内容、项目、关系和后果并明确确认后，可以由应用服务直接创建或修改正式 Entry，不再强制二次确认。

Candidate 仍然是确认前的产品语义，可以在 Draft/Plan 内持久化；只有用户选择 `加入待处理` 时，才创建 pending Candidate 供以后处理。当前已实施的 `draft_candidate` 与历史 pending Candidate 在替代 change 完成前继续有效，不因讨论文档更新而改变。

### 11.3 固定“整理成知识”将被通用操作替代

回答卡常驻的“整理成知识”只支持把一条有 Grove Citation 的回答送入固定 Candidate 流程，无法覆盖无引用开放讨论、用户决定、AI 通用建议、讨论片段选择和准备阶段关系判断。长期应移除这个固定入口，但保留自然语言“把刚才整理成知识”的意图理解。

替代路径是：用户显式请求或接受上下文建议 → `prepare_operation` → Operation Review → 直接确认正式 Entry，或选择加入待处理。底层现有 Run、Draft、恢复、幂等、来源追溯和版本校验能力应尽量复用；在替代能力上线前不直接删除当前唯一可用入口。

## 12. 内容性质、形成来源与正式状态

开放讨论允许模型通用知识、用户陈述与 Grove Evidence 混合。如果把所有内容都压进现有 `main_type` 或 `info_nature`，会混淆“这是什么内容”和“它从哪里形成”。数据与界面至少需要区分内容性质、形成来源和产品生命周期，但不增加统一“真实性核验状态”。

### 12.1 内容性质

```text
事实
经验
个人决策
建议
观点或假设
```

现有 `info_nature` 已覆盖事实、经验、建议和推测，近期只需优先评估增加 `decision`，不先枚举大量细分类别。

### 12.2 形成来源

```text
Grove Evidence
用户陈述
AI 通用知识
外部材料
多种来源混合形成
```

形成来源可以是集合而不是单一枚举。对话 Source 应记录选定消息、模型 provider/model、实际采用的 Grove Evidence、用户编辑和最终确认；AI 通用知识可以参与形成内容，但不能伪装成 Citation。

同一条内容可能是：

```text
内容性质：个人决策
形成来源：用户陈述 + AI 通用建议
```

也可能是：

```text
内容性质：经验
形成来源：用户提供的截图 + 当前讨论
```

### 12.3 正式状态不是客观正确性

正式 Entry 表示用户已经确认“这条内容值得在我的知识库中保留”，不表示 Grove 判定其为客观事实。有 Source 只证明形成材料可追溯；外部网页、截图或其他 AI 输出也不因成为 Source 自动获得更高可信等级。

因此不为 Entry 增加 `verified: true/false` 或统一可信度。服务端仍要校验引用对象、权限、版本和 quote 与原文的对应关系，但这是技术完整性，不是真伪判断。界面优先使用“引用原文”“来源可查看”“来自你的知识”等文案，避免“已验证事实”“可靠来源”等暗示。

## 13. 可追溯性与诚实约束

以下约束不应只依赖提示词：

- 精确总数、占比、排名等数字必须来自服务端确定性统计结果；
- 搜索命中数、快照条数和 Evidence 数量不得被描述为范围总数；
- Citation 必须指向当前 Run 实际读取并完成原文对应校验的真实 Evidence 或未来真实外部材料；
- AI 通用知识必须可识别，不得伪装成 Grove 记录或已经联网查得的材料；
- 结构化工具结果应保存范围、参数、时间和结果句柄，供回答校验与审计；
- 来源差异或冲突必须并列呈现，不由模型静默覆盖用户知识或替用户裁决；
- 没有必要依据时可以继续开放讨论，但进入正式沉淀前必须说明内容性质和形成来源。

## 14. 分阶段功能清单

这份架构是长期方向，不代表一次 change 全部实现。下面按依赖拆成功能阶段；每个阶段仍需再拆成一个或多个 OpenSpec change，不能把整张清单一次实施。

### 14.1 阶段 A：开放讨论与回答依据

- 普通问题允许不调用 Grove 工具，使用模型通用能力讨论；
- 规划时选择 `knowledge_only / knowledge_first / model_first / hybrid` 等依据策略；
- 相关时自主读取 Grove，非个性化问题不强制检索；
- 回答正文直接给结论，不增加重复综合前言；
- 回答下展示紧凑、可展开的依据概览；
- 区分你的知识、用户当前陈述和 AI 通用知识，不为模型知识生成假 Citation；
- 记录 provider、model、fallback、实际工具和依据类型；
- 建立开放讨论、混合依据、用户限制和来源冲突的代表性评估集。

### 14.2 阶段 B1：一次结构化计划与确定性执行（本地完成待验收）

`add-knowledge-agent-structured-query-tools` 已完成这一纵向切片的本地实现与验证，尚未
归档或推送：

- 抽取应用控制的只读工具 registry、dispatcher、调用状态与最小化审计；
- 建立受限 `EntrySetSpec`，范围只由 Run 固化上下文注入；
- 在 entries 分支执行一次结构化计划并严格校验，再按固定顺序组合
  `query_entries`、`aggregate_entries` 与既有语义召回；
- 支持结构化筛选、稳定排序、直接 count/分组和有界 Entry 列表组合；
- 只有纯结构化完整集合返回精确统计；语义 top-k、预算截断和不完整执行返回
  limited/unknown；
- 计划、工具与 v2 结果可持久化、恢复、取消，provider/model/fallback 保持可观测；
- 保持旧客户端、旧 Run、v1 Entry 结果与既有固定检索 Workflow 兼容。

### 14.3 阶段 B2：多轮只读工具规划与 Workflow 迁移（后续）

- 允许 Agent 在白名单内观察工具结果后继续规划或停止，但仍由应用控制范围、预算、
  取消、恢复和最终结果校验；
- 让 quick 与 investigate 渐进复用 B1 工具集，并分别固化轮次和预算；
- 覆盖内容问答、对象查找、筛选、统计、混合问题与失败路径的扩展评估集；
- 在等价能力、恢复语义和灰度验证完成前继续保留现有固定 Workflow。

### 14.4 阶段 C：用户显式整理讨论

- 支持“整理这个决定”“保存这段经验”“整理成方法”“总结本段讨论”等结构化意图；
- 自动选择当前主题中的必要消息，支持通过自然语言调整片段；
- 一次讨论可按未来检索单元形成一条或多条 Draft；
- 对话 Source 记录选定消息、模型信息、所用 Grove Evidence 与用户编辑；
- 准备阶段检索相似 Entry，判断独立、相同、补充或差异；
- 生成动作明确的新增、补充、修订或分别保留 Operation Plan；
- Workspace 范围目标项目不明确时使用结构化选择澄清。

### 14.5 阶段 D：统一 Operation Review 与一次确认闭环

- 对话内展示紧凑操作摘要，Bottom Sheet 或全屏承担完整审阅；
- 新增、补充和修订共享状态、恢复、幂等、版本保护、回执与撤销；
- 用户在完整 Review 中确认后直接创建或修改正式 Entry；
- 提供 `加入待处理`，仅在用户选择稍后处理时创建 pending Candidate；
- 将现有 `draft_candidate` 能力迁移到 `prepare_operation`；
- 替代完成后移除回答卡固定“整理成知识”入口，同时兼容旧历史与 pending Candidate；
- 记录建议展示、点击、忽略/拒绝、Draft 编辑和最终确认行为日志。

### 14.6 阶段 E：非阻塞主动沉淀建议

- 识别较稳定的个人决定、经验和可复用结论；
- 在正常回答后显示一个轻量、内容具体的操作建议；
- 当前目标 Entry 已知时可以建议补充或修订，未知时只建议整理内容；
- 避免连续重复同一建议，不设置僵硬的每话题次数上限；
- 第一阶段只记录行为，不自动学习或自行修改阈值；
- 用真实接受、忽略、拒绝和编辑数据评估后再调整提示策略。

### 14.7 阶段 F：更高风险知识操作

- 单 Entry 移动与归属调整；
- 多 Entry 选择集与失效规则；
- 重复知识合并、保留主体与来源汇总；
- 冲突知识分别保留、修订或合并；
- 移入回收站、恢复和影响预览；
- 批量操作的数量限制、分阶段确认、部分失败恢复与审计；
- 永久删除与外部发布默认不向普通 Agent 开放。

### 14.8 后续独立评估

- 外部搜索、专业数据工具和当前时效材料；
- 主动 Discovery；
- Web 接入同一领域协议后的具体桌面交互；
- 来源可靠性由用户自行备注或评估的必要性；
- 更细内容性质，如个人偏好是否需要独立于个人决定。

每一阶段都应使用代表性场景评估，而不是为单条问法添加路由规则。

## 15. 已确定与仍待落地时决定的问题

### 15.1 已确定的产品决策

- 回答依据默认按整条回答概览，只有来源切换、冲突或时效边界时局部标识；
- 不增加统一核验或可信度状态，正式 Entry 表示用户确认保留；
- Agent 自动选择讨论片段，用户主要通过自然语言调整；
- 用户先同意整理内容，准备阶段再确定新增、补充或修订；
- 一次完整 Operation Review 可以直接形成正式 Entry；
- 主动建议保持轻量，不设置全局关闭选项或僵硬的一次性话题限制；
- 固定“整理成知识”最终废弃，能力并入通用操作协议；
- Web 与原生 App 共享领域协议，但各自使用适合端侧的交互形态。

### 15.2 在对应 change 设计时再决定

1. B2 由独立规划器延续 B1 计划，还是引入可观察工具结果的专用循环协议？
2. quick/investigate 分别允许几轮、多少次工具调用，固定 Workflow 按什么顺序迁移？
3. `respond / entries / prepare_operation` 长期由同一次规划调用决定，还是继续复用现有结果形态路由？
4. 对话 Source、formation basis 与现有 Evidence/EntryVersion 的具体数据结构如何复用？
5. Operation Review 直接创建 Entry 时，目录与关系建议必须在准备阶段完成到什么程度？
6. 旧 `draft_candidate`、pending Candidate、历史消息与客户端版本如何渐进迁移？
7. 多 Entry 操作中哪些可以复用通用 Plan，哪些需要专用领域状态机？
8. 外部工具何时进入路线、如何表达材料时效，以及哪些高风险领域需要额外提示？
