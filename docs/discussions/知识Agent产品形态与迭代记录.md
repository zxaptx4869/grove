# 知识 Agent 产品形态与迭代记录

> 本文档整理 2026-08 围绕「AI 阅读如何演进为知识 Agent」的连续讨论，帮助以后快速回顾产品形态、已完成能力、关键取舍与后续方向。
>
> 本文档是可持续更新的讨论记录，不是产品蓝图或实现规格。产品边界以 `docs/产品蓝图/` 对应专题为准，已实施行为以 OpenSpec 主规格为准，具体 change 的技术取舍以其 `design.md` 为准。

## 0. 当前结论

Grove 的「AI 阅读」不再被理解为目录页面中的一次性问答功能，而是逐步演进为 Web 与原生 App 共用的 **Knowledge Agent（知识 Agent）**：用户可以围绕 Workspace 或项目中的正式知识持续提问、查找证据、发现冲突，并在明确确认后逐步完成知识创建和修订。

原生 App 以对话为主要产品形态，不复制 Web 的完整桌面工作台；Web 最终也应接入同一套知识 Agent 领域协议。对话是统一入口，但回答、草稿、候选、正式知识和操作结果必须使用不同的结构与状态表达，不能混成普通聊天文本。

当前演进策略是：**按一个个可验证的纵向场景逐步增加自主性，而不是先罗列所有工具或一次完成全部知识增删改。**

## 1. 产品形态共识

### 1.1 对话是入口，不代表所有交互都是纯文本

移动端以对话为主，大多数知识动作可以从对话发起，但复杂操作仍需使用结构化界面原语：

- 即时回答与引用；
- 过程状态、知识不足和冲突；
- Entry 或 Candidate 对象卡；
- 可编辑草稿；
- 修改前后差异；
- 明确确认 Sheet；
- 执行回执、错误恢复与撤销。

因此，目标不是把传统页面中的所有按钮改写成聊天命令，而是让用户在对话上下文中完成任务，同时在需要选择对象、检查后果或确认写入时切换到更可靠的结构化交互。

### 1.2 阅读与操作共用会话，但保持行为分层

阅读和知识操作不需要拆成两个完全独立的产品入口，但必须分成不同的行为层：

```text
普通提问
  → Agent 自主使用受限只读能力
  → 返回即时回答与证据

用户显式发起知识操作
  → Agent 生成 Candidate 或 Draft
  → 用户检查对象、内容与影响
  → 用户明确确认
  → 应用服务执行正式写入
  → 返回可审计回执，必要时提供撤销
```

普通 Composer 默认是讨论和阅读入口。当前阶段不根据一句自由文本自动推断并执行写操作，以免把“讨论一下怎么改”误判为“现在就修改”。写入行为由引用、对象卡或明确动作按钮发起。

### 1.3 项目是用户可感知的范围，目录不是对话范围

知识 Agent 的范围只有两级：

- 当前 Workspace 的「全部知识」；
- 当前 Workspace 内的一个具体项目。

Web 与原生 App 使用相同范围语义，不提供目录节点级范围选择。目录层级深、移动端难展示，用户也更常表达主题而不是先定位目录；Agent 应在项目内自动检索相关目录和 Entry。目录仍承担内部定位线索、知识归属和浏览结构，不会被删除。

### 1.4 项目需要存在，但不应频繁打断对话

项目是知识隔离、目标写入、上下文理解和结果归属的重要边界，因此知识 Agent 必须有项目概念。用户可以切换到某个项目，也可以在 Workspace 范围提问；当 Workspace 范围的结果需要创建知识时，再明确选择目标项目。

项目切换是低频的范围控制，不应要求用户为每个问题重复选择。目录定位则交给 Agent 和检索系统完成。

## 2. Agent 的自主程度与控制边界

当前知识 Agent 不是可以任意访问数据库、无限调用工具的开放式 Agent，而是**应用控制边界内的受限自主 Agent**。

| 环节 | Agent 可以决定 | 应用服务负责 |
|---|---|---|
| 上下文理解 | 当前消息是继续、新话题还是需要澄清 | 限制历史长度、隔离范围、持久化决策 |
| 回答方式 | 自动模式下选择快速回答或深度查找 | 固化预算、失败降级和停止规则 |
| 调查 | 根据已见证据提出少量新查询或停止 | 执行固定只读工具链、鉴权、去重、预算和恢复 |
| 回答 | 组织观点、选择允许的 Evidence 句柄 | 核验引用、状态、覆盖、缺口和模型降级 |
| 创建/修改 | 生成候选草稿或修订建议 | 校验对象和 Evidence、事务写入、幂等、版本与撤销 |

核心理解是：**工具决定 Agent 能做什么，场景决定先建设哪些工具。** 不应脱离用户场景先造一个“大而全”的工具箱；每次选择一条黄金路径，补齐它需要的最小工具、状态、审批和评估，再进入下一条。

## 3. 对象与状态语义

对话里会同时出现多种对象，必须让用户能够分辨：

| 对象 | 含义 | 是否正式知识 |
|---|---|---|
| 即时回答 | Agent 针对当前问题生成的阅读结论 | 否 |
| Citation / Evidence | 本次回答实际核验的 Entry 与 Source 原文依据 | 依据本身来自正式数据，但回答仍不是 Entry |
| Draft | AI 生成、可编辑、尚未提交的操作草稿 | 否 |
| Candidate | 已进入待确认流程的候选知识 | 否 |
| Entry | 用户最终确认后的正式知识记录 | 是 |
| 操作回执 | 某次确认、失败或撤销的可审计结果 | 否 |

回答正文应该直接回答问题。范围、检索过程、预算停止原因、覆盖和缺口由结构化区域承载，不应先输出一段重复的“综合性描述”增加阅读负担。

「部分结果」也不是对回答质量的笼统评价。它表示已有内容和引用可用，但在服务端预算内仍有未覆盖问题、冲突或未完成调查；具体原因应在覆盖、缺口与停止说明中展示。

## 4. 已经完成的能力

以下状态以 2026-08-30 已归档 OpenSpec change 为准。

### 4.1 原生移动基础

`add-native-mobile-foundation` 已完成：

- 建立 Expo + React Native + TypeScript 原生工程；
- 建立移动登录、Bearer Session、安全存储和登出；
- 与 Web 共用账号、Workspace、项目和后端业务模型；
- 形成以对话为默认首页的移动壳层；
- 手机 Web 仍不是业务端，原生 App 不使用 WebView 包装 Web。

### 4.2 知识 Agent 只读底座

`add-knowledge-agent-foundation` 已完成：

- 持久化 Conversation、Message、Scope Event 和 Run；
- Run 可以恢复、取消、幂等提交，并限制同会话并发；
- 提供受 Workspace/项目范围约束的正式知识搜索、Entry 读取和 Source Evidence 核验；
- 最终引用只能使用本 Run 实际核验的 Evidence 句柄；
- 搜索、重排、回答的 provider、model、fallback 和错误可观测；
- 用户范围收敛为 Workspace 与项目，不再提供目录节点级选择。

### 4.3 连续追问与显式工作集

`add-knowledge-agent-continuous-follow-up` 已完成：

- 能判断继续当前主题、开始新话题或请求澄清；
- 用户可以显式覆盖自动判断；
- 将省略和指代改写为可独立检索的问题；
- 用版本化工作集保存当前主题涉及的正式 Entry 线索；
- 历史回答只帮助理解意图，不能直接变成本轮事实或引用；
- 范围切换、新话题、失败和澄清有明确的上下文推进规则。

### 4.4 有界深度调查

`add-knowledge-agent-bounded-investigation` 已完成：

- 支持自动、快速回答和深度查找；
- 深度查找可以观察已有证据、发现缺口、补充查询并再次读取；
- 默认最多三轮，并限制查询、Entry 和 Evidence 预算；
- 重复查询、无新增知识或预算耗尽时确定性停止；
- 返回实际模式、轮次、停止原因、覆盖、未解决缺口和冲突；
- 不联网、不写知识、不无限后台运行。

### 4.5 原生 App 真实对话

`add-native-knowledge-agent-conversation` 已完成：

- 支持恢复最近对话、新建对话、历史分页和范围切换；
- 支持真实输入、幂等重试、前台轮询、取消及重启恢复；
- 展示检索、Evidence 核验、调查和综合等可理解过程；
- 展示正常回答、部分结果、知识不足、冲突、失败与澄清；
- Citation 可以打开并区分 Entry、Source 原文快照和当前知识状态；
- 对键盘、输入框、长内容、Bottom Sheet、安全区和触控区域进行过体验优化。

### 4.6 从回答整理为待确认知识

`add-knowledge-agent-candidate-drafting` 已完成：

- 用户可以从有有效引用的回答显式选择「整理成知识」；
- 项目范围回答沿用当前项目，Workspace 范围回答需要明确目标项目；
- Agent 基于允许的 Evidence 生成可编辑 Candidate Draft；
- 用户确认后，应用服务幂等创建可追溯的虚拟 Source、Attachment、Extraction 和 pending Candidate；
- 不直接创建或修改正式 Entry；
- 移动端尚未承担 Candidate 到正式 Entry 的最终确认台闭环。

## 5. 当前“找知识”能力及缺口

### 5.1 已支持：问答式查找

用户已经可以询问：

- 「帮我找一下装修预算这条知识。」
- 「个人健康项目里有哪些和血压有关的知识？」
- 「找出防水施工方面相互冲突的记录。」

Agent 会在当前 Workspace 或项目范围搜索正式 Entry，读取相关内容，给出综合回答并附上实际使用的引用。用户可以打开 Citation 查看 Entry 与 Source Evidence，也可以继续追问。

这种形态适合“找到以后理解它”，但它的主要结果仍是一份回答，不保证把所有匹配 Entry 作为完整、可操作的列表返回。快速回答和深度查找都受检索与 Evidence 预算限制，不能把“相关结果”误解成“穷尽全部结果”。

### 5.2 待讨论：结构化知识查找结果

后续需要考虑第二种结果形态：**查找对象，而不是综合回答。**

```text
用户要求查找一条或多条知识
  → Agent 理解查询条件并检索
  → 返回结构化 Entry 结果卡
  → 用户打开、勾选或缩小范围
  → 对选中对象发起修订、整理或批量操作
```

结果卡可能需要表达：Entry 标题、摘要、项目、目录、匹配原因、来源状态和是否已穷尽；并允许打开、选择、修订或进入后续批量整理。

这个方向已经形成产品共识，但尚未形成正式 change。仍需讨论：

- 由 Agent 自动判断“回答模式 / 找对象模式”，还是提供显式入口；
- 多结果如何分页、继续查找和表达不完整覆盖；
- 对话中的选择是否形成临时对象集，以及何时失效；
- 它单独建设，还是作为多 Entry 整理 change 的前置部分。

## 6. 已规划、尚未实施

### 6.1 单 Entry 修订、确认与撤销

`add-knowledge-agent-entry-revision` 已完成 OpenSpec 规划，尚未开发。

目标路径：

```text
Agent 回答并引用某条 Entry
  → 用户从引用明确选择“修订这条知识”
  → 输入修改要求
  → Agent 基于当前 Entry 与允许 Evidence 生成修订草稿
  → 用户编辑并查看完整差异
  → 用户明确确认
  → 应用服务创建 Entry 新版本
  → 返回操作回执，可在没有后续修改时安全撤销
```

当前规划只允许修订某条已完成或部分完成回答实际引用的 Entry。这样目标由用户明确选择，避免 Agent 猜测对象。普通 Composer 仍然只读。

撤销不是无条件覆盖旧值：如果本次操作后 Entry 又被修改，系统拒绝一键撤销，避免抹掉后来的版本。

## 7. 后续路线草案

以下只是便于延续讨论的轻量记录，顺序和拆分都可能变化，不应直接作为开发任务。

### 7.1 近期闭环

1. 完成 `add-knowledge-agent-entry-revision`，验证第一条正式知识修改工具。
2. 补齐移动端 pending Candidate 的最终确认、拒绝与正式 Entry 归档闭环。
3. 决定结构化“知识查找结果卡”是单独 change，还是与多 Entry 操作共同建设。
4. 建设多 Entry 整理：对象选择、重复合并、冲突保留、分阶段确认、事务执行和恢复。
5. Web 接入统一 Knowledge Agent 对话，并迁移或移除旧 Reader / AI 阅读入口。

### 7.2 更后面的扩展方向

- 在有可靠对象消歧后，允许用户从知识浏览页选择 Entry 与 Agent 讨论或修订；
- 评估自由文本中的写意图识别，但仍不允许绕过预览与人工确认；
- 增加移动、删除、目录调整等更高风险知识工具；
- 接入移动端收集、待处理和知识浏览，但不复制完整桌面工作台；
- 在用户授权、Source 先行和 Candidate 确认的边界下发展联网 Discovery；
- 根据真实使用数据调整调查预算、结果完整性表达和模型分层。

## 8. 尚未锁定的问题

后续讨论可以优先回答这些问题：

1. “找知识”什么时候应该返回答案，什么时候应该返回可选择的 Entry 列表？
2. 单 Entry 修订完成后，下一步优先补 Candidate 最终确认，还是多 Entry 操作？
3. 多 Entry 操作的第一条黄金路径应选“合并重复知识”还是“处理冲突”？
4. Web 的统一对话入口放在全局层、项目层，还是两处共享同一个当前会话？
5. 对话中的结构化对象卡如何在长历史中恢复，避免用户误操作旧对象？
6. 哪些操作可以由 Agent 自动准备，哪些必须先向用户澄清对象、范围或后果？

## 9. 文档维护方式

为了让本文档保持易更新：

- 已归档 change：从“规划/讨论”移动到“已经完成”，只记录用户可感知能力，不复制全部技术任务；
- 新共识：补到“产品形态共识”或对应专题；
- 未确定想法：只放“后续路线草案”或“尚未锁定的问题”，避免提前写成承诺；
- 产品边界改变：先更新产品蓝图权威专题，再同步本文概述；
- 实现细节改变：以主规格和 change `design.md` 为准，本文只链接和摘要。
