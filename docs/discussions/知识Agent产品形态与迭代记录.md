# 知识 Agent 产品形态与迭代记录

> 本文档整理 2026-08 至 2026-09 围绕「AI 阅读如何演进为知识 Agent」的连续讨论，帮助以后快速回顾产品形态、已完成能力、关键取舍与后续方向。
>
> 本文档是可持续更新的讨论记录，不是产品蓝图或实现规格。产品边界以 `docs/产品蓝图/` 对应专题为准，已实施行为以 OpenSpec 主规格为准，具体 change 的技术取舍以其 `design.md` 为准。

## 0. 当前结论

Grove 的「AI 阅读」不再被理解为目录页面中的一次性问答功能，而是逐步演进为 Web 与原生 App 共用的 **Knowledge Conversation Agent（知识对话 Agent）**：用户既可以围绕 Workspace 或项目中的正式知识持续提问、查找对象和发现差异，也可以在没有已有知识或明确任务的情况下与 AI 讨论、答疑和共同形成个人决定、经验或方法。

原生 App 以对话为主要产品形态，不复制 Web 的完整桌面工作台；Web 最终也应接入同一套知识 Agent 领域协议。对话是统一入口，但回答、草稿、候选、正式知识和操作结果必须使用不同的结构与状态表达，不能混成普通聊天文本。

Agent 按问题需要使用用户当前陈述、Grove 知识和模型通用能力，并在回答中透明说明形成依据。Grove 追求可追溯，不替用户判断知识是否客观正确；正式 Entry 表示用户确认值得保留，而不是系统授予“已验证事实”状态。

当前演进策略是：**按一个个可验证的纵向场景逐步增加自主性，而不是一次完成全部知识增删改。**

## 1. 产品形态共识

### 1.1 对话是入口，不代表所有交互都是纯文本

移动端以对话为主，大多数知识动作可以从对话发起，但复杂操作仍需使用结构化界面原语：

- 即时回答与引用；
- 过程状态、知识不足和冲突；
- Entry 或 Candidate 对象卡；
- 可编辑草稿；
- 修改前后差异；
- 明确确认 Sheet；
- 执行回执、错误恢复与撤销。

因此，目标不是把传统页面中的所有按钮改写成聊天命令，而是让用户在对话上下文中完成任务，同时在需要选择对象、检查后果或确认写入时切换到更可靠的结构化交互。

### 1.2 阅读与操作共用会话，但保持行为分层

阅读和知识操作不需要拆成两个完全独立的产品入口，但必须分成不同的行为层：

```text
普通提问或开放讨论
  → Agent 按需使用模型通用能力和受限只读工具
  → 返回即时回答、依据概览与可选轻量建议

用户显式发起或接受知识操作建议
  → Agent 固定讨论对象并准备 Operation Plan
  → 检查相似知识，明确新增、补充或修订关系
  → 用户检查对象、内容、差异与影响
  → 用户明确确认
  → 应用服务执行正式写入
  → 返回可审计回执，必要时提供撤销
```

普通 Composer 默认是讨论和阅读入口。Agent 可以识别自由文本中的明确操作意图，也可以在讨论形成稳定结论后提出非阻塞建议；但识别与建议只进入准备阶段，不能绕过 Operation Review 执行写操作。引用、对象卡和明确按钮继续提供目标更加可靠的结构化入口。

### 1.3 项目是用户可感知的范围，目录不是对话范围

知识 Agent 的范围只有两级：

- 当前 Workspace 的「全部知识」；
- 当前 Workspace 内的一个具体项目。

Web 与原生 App 使用相同范围语义，不提供目录节点级范围选择。目录层级深、移动端难展示，用户也更常表达主题而不是先定位目录；Agent 应在项目内自动检索相关目录和 Entry。目录仍承担内部定位线索、知识归属和浏览结构，不会被删除。

### 1.4 项目需要存在，但不应频繁打断对话

项目是知识隔离、目标写入、上下文理解和结果归属的重要边界，因此知识 Agent 必须有项目概念。用户可以切换到某个项目，也可以在 Workspace 范围提问；当 Workspace 范围的结果需要创建知识时，再明确选择目标项目。

项目切换是低频的范围控制，不应要求用户为每个问题重复选择。目录定位则交给 Agent 和检索系统完成。

## 2. Agent 的自主程度与控制边界

当前知识 Agent 不是可以任意访问数据库、无限调用工具的开放式 Agent，而是**应用控制边界内的受限自主 Agent**。

| 环节 | Agent 可以决定 | 应用服务负责 |
|---|---|---|
| 上下文理解 | 当前消息是继续、新话题还是需要澄清 | 限制历史长度、隔离范围、持久化决策 |
| 回答方式 | 自动模式下选择快速回答或深度查找 | 固化预算、失败降级和停止规则 |
| 调查 | 根据已见证据提出少量新查询或停止 | 执行固定只读工具链、鉴权、去重、预算和恢复 |
| 回答 | 组织观点、选择允许的 Evidence 句柄 | 核验引用、状态、覆盖、缺口和模型降级 |
| 创建/修改 | 识别机会、选择目标并准备 Operation Plan | 校验对象、形成来源、事务写入、幂等、版本与撤销 |

核心理解是：**工具决定 Agent 能做什么，场景决定先建设哪些工具。** 不应脱离用户场景先造一个“大而全”的工具箱；每次选择一条黄金路径，补齐它需要的最小工具、状态、审批和评估，再进入下一条。

## 3. 对象与状态语义

对话里会同时出现多种对象，必须让用户能够分辨：

| 对象 | 含义 | 是否正式知识 |
|---|---|---|
| 即时回答 | Agent 针对当前问题生成的阅读结论 | 否 |
| Citation / Evidence | 本次回答实际核验的 Entry 与 Source 原文依据 | 依据本身来自正式数据，但回答仍不是 Entry |
| Draft | AI 生成、可编辑、尚未提交的操作草稿 | 否 |
| Candidate | 人工确认前的候选内容语义，可以位于确认台或对话 Operation Review | 否 |
| Entry | 用户最终确认后的正式知识记录 | 是 |
| 操作回执 | 某次确认、失败或撤销的可审计结果 | 否 |

回答正文应该直接回答问题。范围、检索过程、预算停止原因、覆盖和缺口由结构化区域承载，不应先输出一段重复的“综合性描述”增加阅读负担。

「部分结果」也不是对回答质量的笼统评价。它表示已有内容和引用可用，但在服务端预算内仍有未覆盖问题、冲突或未完成调查；具体原因应在覆盖、缺口与停止说明中展示。

Citation 与 Source 表达内容从哪里来，不代表 Grove 判断来源可靠。模型通用知识可以参与讨论与形成草稿，但必须与真实 Grove Source 区分，不能伪造引用。服务端所说的 Evidence 校验只确认对象、权限、版本和 quote 与原文对应关系，不代表事实判真。

## 4. 已经完成的能力

以下已完成状态以 2026-09-02 已归档 OpenSpec change 为准。

### 4.1 原生移动基础

`add-native-mobile-foundation` 已完成：

- 建立 Expo + React Native + TypeScript 原生工程；
- 建立移动登录、Bearer Session、安全存储和登出；
- 与 Web 共用账号、Workspace、项目和后端业务模型；
- 形成以对话为默认首页的移动壳层；
- 手机 Web 仍不是业务端，原生 App 不使用 WebView 包装 Web。

### 4.2 知识 Agent 只读底座

`add-knowledge-agent-foundation` 已完成：

- 持久化 Conversation、Message、Scope Event 和 Run；
- Run 可以恢复、取消、幂等提交，并限制同会话并发；
- 提供受 Workspace/项目范围约束的正式知识搜索、Entry 读取和 Source Evidence 核验；
- 最终引用只能使用本 Run 实际核验的 Evidence 句柄；
- 搜索、重排、回答的 provider、model、fallback 和错误可观测；
- 用户范围收敛为 Workspace 与项目，不再提供目录节点级选择。

### 4.3 连续追问与显式工作集

`add-knowledge-agent-continuous-follow-up` 已完成：

- 能判断继续当前主题、开始新话题或请求澄清；
- 用户可以显式覆盖自动判断；
- 将省略和指代改写为可独立检索的问题；
- 用版本化工作集保存当前主题涉及的正式 Entry 线索；
- 历史回答只帮助理解意图，不能直接变成本轮事实或引用；
- 范围切换、新话题、失败和澄清有明确的上下文推进规则。

### 4.4 有界深度调查

`add-knowledge-agent-bounded-investigation` 已完成：

- 支持自动、快速回答和深度查找；
- 深度查找可以观察已有证据、发现缺口、补充查询并再次读取；
- 默认最多三轮，并限制查询、Entry 和 Evidence 预算；
- 重复查询、无新增知识或预算耗尽时确定性停止；
- 返回实际模式、轮次、停止原因、覆盖、未解决缺口和冲突；
- 不联网、不写知识、不无限后台运行。

### 4.5 原生 App 真实对话

`add-native-knowledge-agent-conversation` 已完成：

- 支持恢复最近对话、新建对话、历史分页和范围切换；
- 支持真实输入、幂等重试、前台轮询、取消及重启恢复；
- 展示检索、Evidence 核验、调查和综合等可理解过程；
- 展示正常回答、部分结果、知识不足、冲突、失败与澄清；
- Citation 可以打开并区分 Entry、Source 原文快照和当前知识状态；
- 对键盘、输入框、长内容、Bottom Sheet、安全区和触控区域进行过体验优化。

### 4.6 从回答整理为待确认知识

`add-knowledge-agent-candidate-drafting` 已完成：

- 用户可以从有有效引用的回答显式选择「整理成知识」；
- 项目范围回答沿用当前项目，Workspace 范围回答需要明确目标项目；
- Agent 基于允许的 Evidence 生成可编辑 Candidate Draft；
- 用户确认后，应用服务幂等创建可追溯的虚拟 Source、Attachment、Extraction 和 pending Candidate；
- 不直接创建或修改正式 Entry；
- 移动端尚未承担 Candidate 到正式 Entry 的最终确认台闭环。

这是当前已实施的过渡能力，不再作为长期产品形态：它只支持有 Grove Citation 的单条回答，并要求二次确认。未来由讨论片段 `prepare_operation`、统一 Operation Review 和一次确认正式 Entry 替代；替代完成前继续按现有主规格工作并兼容历史 Candidate。

### 4.7 单 Entry 修订、确认与撤销

`add-knowledge-agent-entry-revision` 已完成：

- 只能从回答实际有效 Citation 明确选择一条 Entry 发起，不从普通文本猜测写意图；
- Agent 基于当前 Entry 和允许 Evidence 生成可编辑 Revision Draft，并提供完整字段差异；
- 用户明确确认后，应用服务原子更新正式 Entry、追加版本并保留/补充真实来源；
- 保存操作前后快照、版本和 Evidence 增量，未发生后续修改时可以安全撤销；
- Entry 已被后来修改或 Evidence 失效时拒绝覆盖，历史与执行回执可以在对话中恢复。

### 4.8 结构化 Entry 查找

`add-knowledge-agent-structured-entry-search` 已完成：

- 普通消息可以自动或按用户覆盖返回综合回答或 Entry 列表；
- Entry 结果以有界快照持久化并随历史恢复，明确区分分页与搜索完整性；
- 结果卡展示正式知识标题、摘要、项目、目录、类型、来源和当前状态；
- 用户可以打开当前 Entry，结果形态不合适时可一键以新消息重发原问题；
- 结果命中不自动推进事实工作集，也不直接获得修订、多选或批量写入权限。

### 4.9 开放讨论与依据透明（实施完成，待归档）

`add-knowledge-agent-open-discussion` 已完成实现与自动化验收，正在本地分支
等待用户验收与归档：

- 普通回答支持依据策略：仅使用 Grove、知识优先、模型优先、混合依据与
  外部材料边界；界面只呈现“自动选择 / 仅使用我的知识库”，并允许
  自然语言明确限制收紧；
- 允许模型优先/混合回答在无 Citation 时按实际完成度正常完成，同时
  Grove Citation 仍只来自当前 Run 服务端核验的 Evidence；
- 当前话题内服务端校验过的用户陈述可作为“你提供的信息”参与回答，
  不包装成 Citation、Source 或正式 Entry；新话题、范围切换与未完成
  澄清会切断继承；
- 每个终态回答持久化 AnswerBasis v1：Grove 数量、用户消息 ID、模型通用
  知识与外部材料状态，历史恢复返回生成时依据；
- 原生 App 回答下展示紧凑依据概览与可展开详情：Grove 打开原引用、
  用户陈述可定位消息、模型知识与外部边界只说明性质；
- 显式深度查找仍真实创建有界 Investigation；自动 model-first 不伪造调查；
- 开放/混合/用户陈述回答不会进入旧“整理成知识”入口，纯 Grove 回答与
  历史回答继续按原规则整理；
- 特性开关关闭时完全沿用既有 Grove-only 行为，数据库与 API 字段向后兼容。

该能力在用户验收前不覆盖主规格；验收通过后归档 change 并同步主规格，
随后生产环境按部署计划开启特性开关。

## 5. 当前查询能力及下一步缺口

### 5.1 已支持：问答式查找

用户已经可以询问：

- 「帮我找一下装修预算这条知识。」
- 「个人健康项目里有哪些和血压有关的知识？」
- 「找出防水施工方面相互冲突的记录。」

Agent 会在当前 Workspace 或项目范围搜索正式 Entry，读取相关内容，给出综合回答并附上实际使用的引用。用户可以打开 Citation 查看 Entry 与 Source Evidence，也可以继续追问。

这种形态适合“找到以后理解它”，但它的主要结果仍是一份回答，不保证把所有匹配 Entry 作为完整、可操作的列表返回。快速回答和深度查找都受检索与 Evidence 预算限制，不能把“相关结果”误解成“穷尽全部结果”。

### 5.2 已支持：结构化知识查找结果

当用户目标是查找对象而不是获得综合回答时，Agent 可以返回结构化 Entry 列表：

```text
用户要求查找一条或多条知识
  → Agent 理解查询条件并检索
  → 返回结构化 Entry 结果卡
  → 用户打开当前 Entry 或缩小范围继续查找
```

当前列表和问答仍建立在固定检索 Workflow 上：它们可以可靠返回有限相关结果，但缺少精确统计、结构化筛选、排序、分组以及“统计后再列对象”等通用组合能力。这也是下一阶段受限工具型 Agent 需要解决的主要查询缺口。

## 6. 新阶段功能路线

以下只是便于延续讨论的轻量记录，顺序和拆分都可能变化，不应直接作为开发任务。

### 6.1 通用只读工具型查询

- 建设受限 `EntrySetSpec`、结构化查询和聚合统计工具；
- 让快速回答与深度调查复用同一工具集，只使用不同预算；
- 支持计数、筛选、排序、分组和与对象列表组合的问题；
- 建立代表性场景评估集，停止按单条问法增加路由规则。

### 6.2 显式整理讨论与通用 Operation Plan

- 支持整理决定、经验、方法或整段讨论；
- 自动选择必要对话片段，并允许自然语言调整；
- 准备阶段检查独立、相同、补充和差异关系；
- 生成新增、补充、修订或分别保留的明确方案；
- 目标、项目或影响范围不明确时才使用结构化澄清。

### 6.3 统一 Operation Review 与一次确认闭环

- 在对话摘要卡、Bottom Sheet 或全屏中审阅对象、内容、差异、形成来源和影响；
- 用户完整确认后直接创建或修改正式 Entry；
- `加入待处理` 才创建 pending Candidate；
- 迁移并最终废弃固定回答动作“整理成知识”与专用 `draft_candidate` 流程；
- 保留旧 Candidate、历史消息和客户端兼容。

### 6.4 主动沉淀建议

- 对稳定的个人决定、经验和可复用结论提供轻量建议；
- 建议本身不创建 Draft，也不阻断对话；
- 先记录展示、接受、忽略、拒绝和编辑日志，再用真实数据人工调节阈值。

### 6.5 更后面的扩展

- 持久对象选择集与多 Entry 操作；
- 重复合并、冲突保留、移动和回收站；
- Web 接入统一 Knowledge Agent 领域协议；
- 移动端收集、待处理和知识浏览；
- 外部搜索、专业工具与主动 Discovery。

完整阶段依赖、功能项和待设计问题记录在 [知识 Agent 开放对话与工具架构](./知识Agent开放对话与工具架构.md#14-分阶段功能清单)。

## 7. 尚未锁定的问题

后续只在进入对应 change 时回答：

1. 开放讨论已由 `add-knowledge-agent-open-discussion` 实施；下一条纵向路径是
   只读工具型查询（`EntrySetSpec`、结构化聚合与统计）还是通用 Operation
   Plan（整理讨论与一次确认），进入对应 change 时再定。
2. 快速模式的调用预算和 `EntrySetSpec` 第一阶段字段边界是什么？
3. 对话 Source 与现有 Evidence、EntryVersion 怎样复用数据结构？
4. 旧 `draft_candidate` 与客户端怎样渐进迁移而不破坏历史？
5. 多 Entry 操作的第一条黄金路径应选合并重复、处理冲突还是移动？
6. 外部工具何时进入路线，哪些时效或高风险问题需要额外边界？

- 未确定想法：只放“后续路线草案”或“尚未锁定的问题”，避免提前写成承诺；
- 产品边界改变：先更新产品蓝图权威专题，再同步本文概述；
- 实现细节改变：以主规格和 change `design.md` 为准，本文只链接和摘要。
