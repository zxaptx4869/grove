## Project Context Snapshot

供多个 Agent 共享的派生上下文，不是正式知识，也不覆盖用户说明。

建议结构：

```text
ProjectContext
├── user_description       用户项目说明，原文优先
├── project_summary        AI 项目概要
├── current_focus          当前关注方向
├── directory_topics       目录主题
├── knowledge_coverage     已确认知识覆盖
├── recent_topics          最近整理主题
├── lifecycle_status       生命周期状态
└── generated_at           更新时间
```

只使用正式目录和已确认 Entry 生成，不使用待确认 Candidate。目录或知识发生重要变化后异步、防抖更新；失败时继续使用上一份有效快照。用户可以查看、纠正和重新生成，纠正内容作为高优先级约束保留。

## Agent 产品架构

产品不向用户强调多个 Agent，但技术职责应分离，不做一个全能 Agent。

| Agent | 核心职责 | 只读上下文 | 输出边界 |
|---|---|---|---|
| Organizing Agent | 解析、语义拆分、价值筛选、项目和目录推荐、关系判断 | Source、项目上下文、目录、已有 Entry | Extraction、Candidate 和归档建议 |
| Directory Agent | 起草、拓展和调整目录 | 项目上下文、目录、已确认 Entry、Source 摘要 | Directory Draft 与结构化操作 |
| Knowledge Agent（Reader 演进） | 开放讨论、Workspace 或项目内查询、连续追问、受限调查与知识操作准备 | 用户当前陈述、已确认 Entry、真实 Source、项目上下文与模型通用能力 | 可恢复的即时答案、对象结果与待确认 Operation Plan；正式写入必须经过用户审阅确认 |
| Discovery Agent | 识别缺口、经授权研究外部来源 | 项目上下文、目录、已确认 Entry | 新 Source、Candidate 和发现报告 |

### PydanticAI 的角色

Grove 同时是 PydanticAI 的学习与实践项目，但产品需求决定技术使用方式：

- 用 Pydantic 模型定义 Agent 依赖、工具参数和结构化输出；
- Agent 负责理解、推理、工具选择和生成草稿；
- 普通应用服务负责权限、持久化、事务、幂等和正式数据校验；
- Agent 可以自主使用白名单只读工具；写能力只允许准备 Candidate、Draft 或 Operation Plan，不向模型暴露绕过确认的最终提交工具；
- 确认正式 Entry 或 Directory 的动作由应用服务在用户操作后执行；
- 不为了“像 Agent”引入自主循环、多 Agent 协商或后台无限任务。

### Knowledge Agent 的演进边界

Knowledge Agent 是 Web 与原生 App 共用的知识交互能力，不再把“AI 阅读”理解成某个目录页面上的一次性生成器。用户可选范围只有当前 Workspace「全部知识」和具体项目；目录继续存在，但仅承担 Agent 内部检索定位、结果归属和知识浏览，不作为对话范围选择项。

Knowledge Agent 的默认能力不只是在 Grove Entry 中寻找答案。普通讨论可以按问题需要使用用户当前陈述、Grove 知识和模型通用能力；未来接入外部工具后再使用真实外部材料。回答必须简洁说明采用了哪些依据：Grove 引用只能指向实际读取的 Source 原文，模型通用知识必须可识别但不得伪造 Citation。这里表达的是形成依据与可追溯性，不为来源设置统一可信等级，也不把有来源包装成客观正确。

演进按可验证纵向能力逐步推进：

1. 先建立持久化对话、独立问题的只读 Run、可信检索工具与可核验 Evidence；每个问题独立检索，不把历史回答当作正式知识。
2. 再增加追问关系判断、显式工作集和有限上下文，让用户能够围绕同一主题连续提问。每条消息明确判断为继续、新话题或需要澄清；用户可以覆盖自动判断。工作集只保存当前主题涉及的正式 Entry 线索并按 Run 版本化，历史回答只帮助理解指代，不能直接成为事实或复用为新引用。
3. 在上述基础上增加有轮次上限的受限自主调查。每条消息可请求自动、快速回答或深度调查：快速回答沿用单轮检索；自动模式由独立结构化路由选择且失败显式回退快速回答；深度调查默认最多三轮。每轮模型只观察当前 Run 的查询与证据账本，提出少量新文本查询或选择回答/知识不足，应用层始终控制固定只读工具链、可信范围、去重、预算与停止。重复查询、无新增知识、达到轮次/查询/对象/Evidence 上限都会确定性停止，并向用户返回实际模式、轮数、停止原因和未解决缺口；仍不允许联网、写知识或后台无限运行。
4. 区分“回答问题”和“查找知识对象”。普通消息默认由独立结构化路由选择综合回答或 Entry 结果列表，用户可以显式覆盖；查找结果只包含当前范围内正式 Entry，以有界快照和完整性状态表达，不把 top-k 包装成全部，不因命中自动推进事实工作集。
5. 知识增删改始终作为独立工具族建设。AI 只能识别机会并准备 Candidate、Draft 或 Operation Plan，正式写入继续由应用服务校验并由用户确认。结构化查找结果不会自动获得写权限；对象选择、修订与多 Entry 操作分别建立明确授权和确认协议。对话中的 Operation Review 可以承担完整人工确认并在一次确认后形成正式 Entry，不强制再进入第二个确认台；用户选择稍后处理时才创建 pending Candidate。

开放讨论中的沉淀建议必须非阻塞。Agent 可以在形成较稳定的个人决定、经验或可复用结论时建议“整理这个决定”“保存这段经验”等，但建议本身不创建草稿；用户接受或显式发起后，应用再进入 `prepare_operation`。目标未知时先表达要整理的内容，准备阶段再检查新增、重复、补充或修订关系；目标 Entry 已知时可以直接提出具体操作，但仍需重新校验版本。

固定挂在回答卡上的“整理成知识”只属于早期纵向能力，不是长期产品入口。长期由自然语言请求、上下文相关的轻量建议和统一 Operation Review 替代；既有 `draft_candidate`、pending Candidate 与历史记录在迁移完成前继续按主规格工作。

一次 Run 的执行记录必须可持久化、可恢复、可取消，并分阶段记录搜索、重排、工具与回答模型的 provider、model、fallback 和错误。模型不能自行指定 Workspace 或项目范围，也不能仅凭猜测的对象标识读取知识。

最终 Grove 引用必须来自本 Run 实际读取并完成原文对应校验的 Source/Attachment Evidence。模型只选择服务端生成的 Evidence 句柄，不能自由生成 `quote`；无法确认引用关系的内容不能包装成 Source 原文。这里校验的是对象、权限、版本和原文对应关系，不代表 Grove 对内容真伪作出判断。

连续追问也不降低这条证据边界：上一轮工作集只提供检索种子，本轮必须重新校验 Entry 范围、重新读取 Source/Attachment 并生成新的 Run Evidence。范围切换和用户显式开始新话题会切断旧工作集；失败或澄清不推进上下文，无有效引用时不能加入任何 Entry，但新话题可保留一个不作为事实的空主题标签以理解下一句指代。

受限调查同样不建立跨 Run 事实记忆。调查账本只属于当前 Run，用来记录逐轮查询、已发现 Entry、当前 Run Evidence、覆盖、缺口与冲突线索；历史助手回答、历史 Evidence 和控制器摘要都不能变成事实。崩溃恢复复用已完成轮次，从下一未完成步骤继续；取消保留已提交轮次供审计，但不产生正常回答或推进工作集。只有最终回答实际有效引用的 Entry 才可进入输出工作集，搜索命中本身不代表主题成员。

### 公共上下文

多个 Agent 共享 Project Context Snapshot，避免各自对项目作出相互矛盾的总结。用户项目说明始终具有最高优先级，AI 项目理解可以自动刷新但必须可见、可纠正。
