## 结果

12 段场景各运行 2 次，共 24 个独立 Conversation、54 个计划轮次。

| 指标 | 结果 |
|---|---:|
| 实际发送问题 | 48 |
| 自动检查通过 | 3 |
| 自动检查失败 | 45 |
| 前序失败后跳过依赖追问 | 6 |
| 整段自动通过 | 0 / 24 |
| 不必要澄清 | 37 |
| 单轮耗时中位数 | 3.06 秒 |
| 单轮最大耗时 | 11.15 秒 |

这是针对连续对话薄弱点的评测集，含当前尚未提供的项目分组/项目解析能力，不能
把上述比例外推为 Grove 全部问题的成功率。多数请求在上下文阶段就结束，短延迟
不能解释为完成任务的速度快。API 终态 44 个 completed、4 个 partial，不等于产品
目标通过；其中绝大多数 completed 只是完成了一次澄清回复。

83 条阶段记录中有 76 条 deepseek-chat、4 条 embedding、3 条服务端记录；其中
4 条复合规划记录和 1 条服务端记录标为 fallback。只有 9 条记录包含 usage，无法
给出完整 token 消耗或费用估算。

三个通过轮次分别为：明确列出四种类型的 Workspace 总数（Run 188），以及首轮
确实缺乏指代对象时提出澄清（Run 200、224）。Run 188 的同文重复 Run 212 仍发生
不必要澄清，说明首轮理解也存在波动。

## 已定位问题

### 1. 当前项目未进入上下文决策输入

Conversation 93、105 已通过 API 选中房子装修，用户询问当前项目 method 总数，
Run 194、218 仍追问当前项目名称。最近五条列表、空项目及界面切换范围也出现相同现象。

[Runner](../../backend/app/services/knowledge_agent/runner.py) 在上下文决策处只传入
消息、活动主题、工作集标题和历史；
[上下文提示装配](../../backend/app/agents/knowledge_context.py) 没有当前范围名称。
Workspace id 用于选模型不等于模型收到了当前 Workspace/项目语义。

影响：本可直接执行的首轮问题被提前截断，后续工具根本没有机会运行。

### 2. 统计或澄清后无法稳定继续

原始三轮对话在 Conversation 89、101 重复出现：第一轮统计，第二轮不必要澄清，
第三轮提示“当前没有进行中的主题”。补充完整统计要求的 Conversation 97、109
也未恢复正常执行。

[追问归一化](../../backend/app/services/knowledge_agent/follow_up.py) 在没有活动主题
时会把 continue 改成澄清，而 Runner 从事实工作集版本取得主题。统计结果不推进
事实工作集，与“对话必须可以继续”的需求产生衔接缺口。上下文模型本身也会对
已经明确的统计口径提出多余问题，因此不能仅修一个最终分支。

### 3. “知识”被擅自限定为单一类型

Run 185、209 对“全部项目一共有多少条知识”均返回 36；真实集合是 92。
结构化计划包含 `main_types=[knowledge]`，说明 SQL 数字正确，但用户意图被缩窄。
显式列出四种类型时 Run 188 能正确返回 92，不能要求日常用户必须这样表达。

### 4. 通用知识请求被规则误判成只能查知识库

Run 197、199、221、223 明确要求只用通用知识、不查知识库，仍然进入个人知识
检索并产生 partial。记录显示复合计划校验失败：“回答义务 r1 要求 Grove，但
没有关联只读输入”，随后回退到知识检索路径。

[依据限制识别](../../backend/app/services/knowledge_agent/basis.py) 的
`_EXCLUSIVE_KNOWLEDGE_PATTERN` 会把“只用通用知识”中的“知识”也当成个人知识库。
对原始输入直接调用 `contains_knowledge_only_restriction(...)` 返回 True，
已用本地确定性检查复核。此处是应用规则错误，不能简单归因于模型没听懂。

### 5. 指定项目时可能只得到碰巧正确的数字

Run 208 的独立问题明确是房子装修项目总数，实际 `entry_result.set_summary`
仍是 workspace、project_id=null，结构化计划也没有项目筛选，但返回 92。
因为 demo 只有这个项目有记录，数字恰好一致。最终评分器已将该轮从 pass 改为 fail。

当前 [结构化工具](../../backend/app/services/knowledge_agent/structured_query_tools.py)
分组仅包含类型、信息性质和更新时间月份，不支持项目分组；模型也不能自行在
EntrySetSpec 中传项目标识。需要区分自然语言对象解析、授权范围内的子集筛选，
以及擅自扩大范围，不能靠要求用户重述解决能力缺失。

## 后续优化顺序

1. 给上下文决策提供服务端可信的当前范围，并明确普通查询无需用户重复提供界面已选项目。
2. 明确对话主题、统计集合、待澄清任务与事实工作集的独立职责，补齐追问和澄清恢复。
3. 修正依据限制识别及失败回退，避免把通用知识请求反转为知识库限定。
4. 明确“全部知识”的类型语义，再补项目解析和项目分组工具能力。
5. 用相同场景和数据重跑，前序通过后再评价对象指代、解释自然度和完整任务完成情况。

以上为基于实际结果的优化建议，本轮未实施业务修复，未新增或修改正式变更计划。
