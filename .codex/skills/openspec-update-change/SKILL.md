# 更新 OpenSpec 计划

批准与任务衔接遵循 [AGENTS.md](../../../AGENTS.md)。本阶段只修订规划工件；不把一次计划更新扩展为未经请求的功能实施或全库审计。

## 读取与分析

1. 沿用用户指定或本任务已经明确的 change。指代无法唯一确定时查询 `openspec list --json` 并请求选择，不按最近修改时间推荐或自动选定。
2. 首次或状态变化时用 `openspec status --change <name> --json` 获取实际路径，编辑 `existingOutputPaths` 指向的具体文件，不写 glob 路径。用户指定独立 store 时先发现其 ID，并在支持的命令上保留 `--store <id>`。
3. 具体修改从受影响工件和段落开始，搜索相关术语、需求及引用，核对关联影响；涉及范围、关键决策或发现冲突时再扩大读取。用户要求全面一致性审阅时才系统检查全部工件。复用已读且未变化的内容。
4. 区分必要修改、可选建议与缺失工件；保持 proposal、specs、design、tasks 的关联一致。意图发生根本变化时解释沿用或新建 change 的取舍，不自动另起任务。

## 审阅与写入

- 一次展示跨工件的修改范围、关键差异及理由。用户整体或部分批准后统一写入，已有批准覆盖的修改不逐文件再次确认；未批准或拒绝的修改不写入。
- 大幅重写时才重新获取对应 `openspec instructions <artifact-id> --change <name> --json`；沿用未变化的模板和规则，内容与变更复杂度相称。
- 本阶段修改已有工件。确需新增工件时纳入整体建议；用户已授权补齐后，由规划阶段创建并核对依赖，不依赖当前环境不存在的工具或命令。
- 任务勾选与真实验证结果记录按已有实施授权处理，不触发本技能的计划审批。
- 修改后按影响校验；未改变的工件不为格式统一而重写，未涉及的需求和场景保留。报告实际差异与剩余事项。

## 阶段衔接

用户只要求审阅或计划更新时，交付该范围结果；已授权完整实施时，在计划修改获得必要批准后继续相应实施和验证。需要人工验收或归档批准时准备完整材料，不强制用户逐阶段发送命令。
